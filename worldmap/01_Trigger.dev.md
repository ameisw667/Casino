## 4. Anforderungen

- Task liest ausschließlich `users`, `wallet_transactions`, `game_rounds` (dieselben Tabellen wie die bestehende Admin-Analytics-Route) — keine `INSERT`/`UPDATE`/`DELETE`, kein Aufruf von Bet-/Settlement-/Wallet-RPCs.
- `SUPABASE_SERVICE_ROLE_KEY` wird ausschließlich als Trigger.dev-Secret hinterlegt — nie im Task-Code, nie im Repo, nie im Terminal-Log.
- Telegram-Nachricht enthält ausschließlich aggregierte Kennzahlen (aktive User-Anzahl, Bet-Anzahl, GGR, Top-Spiel) — keine einzelnen User-IDs, E-Mails oder sonstige PII.
- Task-Code lebt versioniert im Repo (z. B. `src/trigger/daily-activity-digest.ts`), nicht nur im Trigger.dev-Dashboard.
- Der Scheduled Trigger wird erst nach mindestens einem erfolgreichen manuellen Testlauf, einem nachgewiesenen Retry-Fall und abgeschlossenem Security-Reviewer-Durchlauf aktiviert.
- Der Task ist idempotent gegenüber Doppelläufen am selben Kalendertag (Retry oder überlappender Cron darf keine doppelte Telegram-Nachricht erzeugen). **Umsetzung ohne neue DB-Persistenz** (Scope-Grenze Abschnitt 2 bleibt bestehen): `sendTelegramMessage()` ist die letzte Aktion im Task, danach folgt kein Code mehr, der werfen und einen Retry der ganzen Run auslösen könnte — ein erfolgreicher Versand kann dadurch nicht durch einen nachfolgenden Fehler ein zweites Mal ausgelöst werden.
- Kein Secret im Klartext in dieser Datei, im Terminal-Output oder im Git-Verlauf.
- Status in der Übersichtstabelle wird erst nach echtem Nachweis (nicht nach Versuch) von 🔴 auf 🟢 gesetzt.

## 9. Entscheidungen (auf Jans Wunsch von Claude getroffen, 2026-08-18)

Jan hat diese drei Punkte explizit an Claude zur Evaluierung/Entscheidung delegiert, statt sie selbst festzulegen. Dokumentiert hier statt in Abschnitt „Offene Punkte", weil sie damit keine offenen Punkte mehr sind — bei künftigem Widerspruch zur tatsächlichen Nutzung jederzeit revidierbar.

- **Admin-Chat-ID → neuer dedizierter Env-Var `TELEGRAM_ADMIN_CHAT_ID`.** Begründung: entkoppelt den Ops-Report vom User-Opt-in-Modell `telegram_links` (Migration 025). Würde Jan als Spieler seine eigenen Big-Win-Notifications testweise deaktivieren, liefe sonst auch der Admin-Digest stillschweigend mit aus — zwei unterschiedliche Zuständigkeiten sollten nicht denselben Schalter teilen. Einmaliger manueller Chat-ID-Lookup (z. B. via `getUpdates` nach einer Testnachricht an den Bot) genügt, kein neuer Code-Pfad in `telegram-link.ts` nötig.
- **Uhrzeit → 08:00, Zeitzone `Europe/Berlin`.** Begründung: Der Digest deckt den vorherigen vollständigen Tag ab (siehe nächster Punkt) — 08:00 liefert einen Morgen-Überblick, ist aber spät genug, dass der Vortag zum Run-Zeitpunkt sicher abgeschlossen ist. `schedules.task()` unterstützt IANA-Zeitzonen nativ (`timezone: "Europe/Berlin"`), keine manuelle UTC-Offset-Umrechnung nötig.
- **Zeitraum „letzte 24h" → vorheriger vollständiger Kalendertag UTC (00:00–24:00 UTC).** Begründung: `src/lib/admin/analytics.ts` bucketet Retention-Cohorts bereits über eine `utcDay()`-Hilfsfunktion nach UTC-Kalendertag — dieselbe Konvention wiederverwenden statt eine zweite, abweichende Zeitfenster-Logik einzuführen. Deterministisch, reproduzierbar, und die Idempotenz-Prüfung (Abschnitt 4) wird einfacher: ein Kalendertag = ein Report, kein Grenzfall durch ein wanderndes Fenster.

**Falls sich einer dieser Punkte nach dem ersten echten Lauf als unpraktisch erweist** (z. B. Uhrzeit passt nicht zu Jans Tagesablauf), ist das eine reine Konfigurationsänderung in Schritt 8 — kein Scope- oder Architektur-Rework.

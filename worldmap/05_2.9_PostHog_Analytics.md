## 2 — Ziel

Den Produktweg `Landing → CTA → Sign-up → erster Spielstart → Stats` messbar machen, ohne PostHog zu einer zweiten Wallet-/Nutzerdaten-Autorität zu machen. PostHog ist reines Lernsystem für Product-Analytics (Funnel/Retention-Denken), kein Ersatz für Sentry (Fehler) oder die bestehende Admin-BI (2.5, geschäftskritische Kennzahlen bleiben in Supabase).

## 3 — Architektur

### 3.1 Consent-Gate

- Default **aus**. Kein Event vor expliziter Zustimmung — auch kein anonymes.
- Zustimmung wird client-seitig unter einem versionierten Key gespeichert (`localStorage`, z. B. `consent.posthog.v1`). Eine künftige Änderung der Datenschutzerklärung erhöht die Version → Banner erscheint erneut.
- Kein Pre-Ticking, keine impliziten Muster. Ablehnen ist genauso leicht erreichbar wie Zustimmen.
- **Cross-Tab-Sync (Review-Fund):** `localStorage`-Writes lösen im schreibenden Tab kein `storage`-Event aus — andere bereits offene Tabs mit aktiver PostHog-Instanz würden einen Opt-out sonst nicht sofort mitbekommen. Ein `window.addEventListener('storage', …)`-Handler prüft bei jeder Änderung erneut den Consent-Status und ruft bei Opt-out `posthog.opt_out_capturing()` in jedem offenen Tab auf.
- **SSR-Sicherheit (Review-Fund):** `localStorage`-Zugriff ausschließlich hinter `useEffect`/`typeof window !== 'undefined'`, um Next.js-App-Router-Hydration-Mismatches (Banner-Flackern, abweichender Server-/Client-Zustand) zu vermeiden.
- Banner-Copy ist ein rechtlicher/redaktioneller Text — **deine Aufgabe**, nicht meine (siehe §6).

### 3.2 Event-Allowlist als Compile-Time-Grenze

Kein `posthog.capture(beliebigerString, beliebigesObjekt)` irgendwo im Code verstreut. Ein einziger Wrapper `trackAllowedEvent()`, dessen Signatur ausschließlich die 5 in der Zukunftsplanung festgelegten Events als Union-Type kennt:

```
type AllowedAnalyticsEvent =
  | { name: 'landing_viewed' }
  | { name: 'cta_play_now_clicked' }
  | { name: 'sign_up_completed' }
  | { name: 'first_game_started'; props: { game: GameType } }
  | { name: 'stats_viewed' }
```

- Kein Event nimmt Freiform-Properties entgegen — nur die hier explizit deklarierten Felder.
- Zod validiert den Wrapper-Input zusätzlich zur Compile-Zeit-Typisierung.
- **Autocapture ist global deaktiviert** (`autocapture: false`, `capture_pageview: false`, `disable_session_recording: true`). Nur die 5 expliziten Custom-Events existieren.

**Wichtiger Review-Fund — diese Allowlist deckt nicht alles ab:** Sie beschränkt nur Felder, die der App-Code selbst konstruiert. Sie verhindert nicht, dass die PostHog-SDK selbst standardmäßig Kontext-Properties an _jeden_ `capture()`-Aufruf anhängt (`$current_url`, `$pathname`, `$referrer`, `$referring_domain`, `$browser`, `$os`, `$device_type`, sowie serverseitig per GeoIP aus der Roh-IP berechnete `$geoip_*`-Felder) — unabhängig von `autocapture`. Das ist ein separater Mechanismus. IP-Adresse ist für sich genommen personenbezogen; kombiniert mit einer stabilen HMAC-`distinct_id` entstünde ein deutlich reichhaltigeres Profil als die "5 unkritische Events"-Formulierung in §2 suggeriert.

**Fix (verbindlich, nicht optional):**

- `posthog.init(..., { ip: false })` bzw. äquivalente aktuelle SDK-Option zum Verwerfen der Client-IP, **zusätzlich** das PostHog-Projekt-Setting "Discard client IP data" aktivieren (SDK-Flag allein reicht nicht, wenn ein Request die IP dennoch mitschickt).
- `$current_url`/`$referrer` von Query-Strings bereinigen (`sanitize_properties`/`property_denylist` bzw. aktuelles SDK-Äquivalent), da interne URLs Session-/Token-Query-Parameter enthalten könnten.
- Diese Konfiguration ist Teil von M6 und hat einen eigenen Negativtest in M12, nicht nur eine Doku-Zeile.

### 3.3 Pseudonyme Identifikation (Wiederverwendung des 2.7-Musters, mit wichtigem Unterschied)

`sign_up_completed` und `stats_viewed` sind auf einen Nutzer bezogen. Die rohe Supabase-`user.id` darf laut Sicherheitsgrenze nicht extern bei PostHog landen.

- Neuer, dedizierter Secret `POSTHOG_DISTINCT_ID_HMAC_SECRET` (nicht identisch mit `GUIDE_TELEMETRY_HMAC_SECRET` — getrennte Secrets pro Zweck, unabhängige Rotation).
- Neue, auth-gated Route `GET /api/analytics/identity` gibt ausschließlich `{ distinctId: HMAC-SHA256(secret, userId), version }` zurück. **Muss in `PUBLIC_ROUTES` in `src/proxy.ts` eingetragen werden** (Review-Fund: sonst liefert die Middleware bei fehlender Session einen HTML-307-Redirect statt eines JSON-401, analog zu allen anderen `/api/casino/*`- und `/api/user/*`-Routen — der `.json()`-Parse im Client würde sonst werfen). Route läuft außerdem durch das bestehende `enforceRateLimit`, wie jede andere API-Route im Projekt (Review-Fund: bislang die einzige API-Route ohne dieses Pattern im Plan).
- Client ruft diese Route einmal pro Session, erst nach erteiltem Consent, cached das Ergebnis in-memory, ruft danach `posthog.identify(distinctId)` auf.
- Anonyme Events vor Login (`landing_viewed`, `cta_play_now_clicked`) laufen ohne `identify()`; PostHog merged sie beim späteren `identify()`-Aufruf automatisch.

**Wichtige Klarstellung (Review-Fund, damit hier keine falsche Sicherheit entsteht):** HMAC verhindert, dass PostHog (oder ein PostHog-Datenleck) die rohe Supabase-User-ID direkt zurückgewinnt. Es verhindert **nicht**, dass PostHog ein dauerhaftes Verhaltensprofil pro Nutzer über Sitzungen hinweg aufbaut — genau das ist der beabsichtigte Zweck für Funnel-Messung (eine stabile, deterministische ID statt einer rotierenden). Das ist eine bewusste, für den Zweck angemessene Design-Entscheidung, aber keine Anonymisierung im strengen Sinn.

### 3.4 `first_game_started` — vereinfachtes Design nach Review (kein Server-zu-PostHog-Call)

**Ursprünglicher Entwurf verworfen:** Die erste Fassung sah einen serverseitigen `posthog-node`-Aufruf direkt aus `bet/route.ts`/`blackjack/route.ts` vor, analog zum 2.7-Telemetrie-Hook. Zwei unabhängige Reviews fanden das unangemessen für diesen Fall:

1. **Der Vergleich mit 2.7 trägt nicht:** 2.7 braucht einen serverseitigen Call, weil die Daten (Token-Usage) nur der Server kennt. Hier weiß der Client bereits, dass der Bet erfolgreich war (er hat gerade ein `200` erhalten) — es fehlt ihm nur ein Boolean ("war das mein erster Bet?").
2. Ein serverseitiger `posthog-node`-Call hätte in einer Vercel-Serverless-Function ein reales Zustellungsrisiko: `posthog-node` batcht standardmäßig und flusht periodisch im Hintergrund — beendet die Function vorher, geht das Event ohne explizites `flushAt: 1`/`await shutdown()` stillschweigend verloren. Das hätte jeden Test bestehen und in Produktion trotzdem nie ankommen können.
3. Der Money-Pfad hätte eine zusätzliche ausgehende Netzwerkabhängigkeit zu einem Drittanbieter bekommen — unnötig, wenn die gleiche Information billiger als reines Response-Feld transportierbar ist.

**Neues Design:** Die bestehende Bet-/Blackjack-Response (die der Client ohnehin für den Wallet-Snapshot erhält) bekommt ein **additives** Feld `isFirstBet: boolean`. Berechnung: eine einfache `EXISTS`-Prüfung (nicht volles `COUNT`, günstiger) auf bestehende Tabellen (`wallet_transactions`/`game_rounds`) für den User, ausgeführt **nach** `settleBet()`/`settleRound()` — **und zusätzlich hart gegated auf `settlement.replayed === false`** (Review-Fund: die Settlement-RPC ist bereits idempotent pro `(user_id, request_id)`; ein Retry des exakt gleichen ersten Bets liefert `replayed: true` und darf `isFirstBet` niemals erneut als `true` auslösen, sonst feuert der Client bei jedem Netzwerk-Retry erneut).

- **Concurrency-Sicherheit ist kein Zufall, sondern eine explizite Abhängigkeit:** Migration `007_server_authority.sql` hält pro User einen `pg_advisory_xact_lock` über die volle Settlement-Transaktion. Zwei parallele erste Bets desselben Users werden dadurch strikt serialisiert — der zweite `settleBet()`-Aufruf startet nachweislich erst, nachdem der erste committed und seinen Lock freigegeben hat. Der `EXISTS`-Check danach ist deshalb race-frei, **aber nur, solange diese Lock-Reichweite unverändert bleibt** — kein neuer Code-Pfad darf `settleBet()` außerhalb des gesperrten Bereichs aufrufen.
- Keine neue Tabelle, keine RPC-Signaturänderung, keine neue Migration — reine Zusatzberechnung im bestehenden API-Route-Handler.
- **Auslösung bleibt client-seitig:** Der Client erhält `isFirstBet` im normalen Bet-Response, prüft Consent lokal (kein Header-Trick auf dem Money-Pfad nötig) und ruft bei `isFirstBet === true` den ganz normalen, bereits vorhandenen `trackAllowedEvent()`-Wrapper mit dem gecachten `distinctId` auf — exakt der gleiche Codepfad wie bei den anderen 4 Events, kein Sonderfall.

Das eliminiert gleichzeitig: den serverseitigen `posthog-node`-Client (nicht mehr benötigt), das Konsens-Header-Problem (siehe unten) und das Serverless-Flush-Risiko.

**Vorher geplanter, jetzt entfallener Mechanismus:** Ein Consent-Flag als Header an die Bet-Anfrage war im ursprünglichen Entwurf vorgesehen, um serverseitig "verifizieren" zu können. Review-Fund: Da §11 bewusst gegen eine serverseitige Consent-Audit-Tabelle entscheidet (kein neues DB-Objekt für v1), gäbe es serverseitig nichts, wogegen ein Header wirklich verifiziert werden könnte — nur Format-/Presence-Check, keine echte Verifikation. Mit dem neuen client-seitigen Auslösungsmodell entfällt dieses Problem vollständig: Consent-Prüfung passiert exakt dort, wo sie für alle anderen Events auch passiert.

### 3.5 Ingest-Pfad: direkt, kein Reverse-Proxy (v1)

Für v1 bewusst nicht gebaut (YAGNI). Bei späterem Bedarf additive Erweiterung, kein Umbau.

### 3.6 CSP-Anpassung

`src/proxy.ts` (bestehende CSP, siehe 1.9-Präzedenzfall für Sentry-Ingest-Host):

- `connect-src` erweitert um den PostHog-Ingest-Host der gewählten Region (exakter Hostname wird bei Account-Erstellung im PostHog-Projekt bestätigt, nicht blind übernommen — kein Wildcard-Host).
- Kein neuer `script-src`-Eintrag nötig: `posthog-js` wird als npm-Paket importiert, kein externes `<script>`-Tag.
- Test-Erweiterung in `src/lib/security/__tests__/proxy-security-headers.test.ts`.
- _Nachrichtlich, nicht Teil dieses Scopes:_ Die bestehende CSP nutzt bereits `'unsafe-inline' 'unsafe-eval'` in `script-src` statt eines Nonce-Musters — ein vorbestehender Zustand, den diese Initiative nicht verschlechtert, aber auch nicht behebt.

### 3.7 Bundle-Budget

`posthog-js` per `dynamic import()` nachladen, ausschließlich nach erteiltem Consent. Kein Impact auf Landing-Page-Erstladung für nicht zustimmende Nutzer.

### 3.8 Erasure (Review-Fund — im Erstentwurf komplett gefehlt)

2.7 hat einen expliziten Löschpfad (Akteur-Hash-Löschfunktion, an den bestehenden Nutzerlöschprozess angebunden) als hartes Go-live-Gate. 2.9 braucht das Äquivalent: Da `distinctId` deterministisch aus der Supabase-`user.id` berechenbar ist, kann bei einer Löschanfrage der gleiche Hash serverseitig neu berechnet und PostHogs Personen-Lösch-API (Delete-Person-by-`distinct_id`) aufgerufen werden.

- Anbindung an den bestehenden Nutzerlöschprozess (der gleiche, den 2.7 bereits nutzt), nicht als neuer eigenständiger Prozess.
- Zusätzlich: PostHog-Projekt-Retention-Einstellung (TTL) als zweite Sicherheitsebene dokumentieren, unabhängig vom expliziten Löschpfad.

## 4 — Anforderungen

### 4.1 Funktional

- F1: Ohne Consent wird kein Netzwerk-Request an PostHog gesendet (auch kein anonymer).
- F2: Genau die 5 freigegebenen Events sind auslösbar, kein weiterer Event-Name ist im Code erreichbar.
- F3: Kein Event-Payload enthält Wallet-Saldo, Bet-Betrag, E-Mail, rohe User-ID, **IP-Adresse/GeoIP oder unsanitisierte URL/Referrer-Query-Strings**.
- F4: `first_game_started` wird genau einmal pro User ausgelöst — sichergestellt durch `isFirstBet`-Berechnung nach `replayed === false` **und** die Serialisierungsgarantie aus Migration 007 (§3.4), nicht nur behauptet.
- F5: Opt-out verhindert alle künftigen Events sofort **im aktuellen Tab**; andere offene Tabs stoppen spätestens beim nächsten `storage`-Event (§3.1).

### 4.2 Nicht-funktional

- N1: Autocapture, Pageview-Autocapture und Session Replay sind global deaktiviert.
- N2: Kein neuer ausgehender Netzwerk-Call vom Money-Pfad (`bet`/`blackjack`-Route) zu einem Drittanbieter — `isFirstBet` ist ein reines Response-Feld.
- N3: `POSTHOG_DISTINCT_ID_HMAC_SECRET` ist server-only, mindestens 32 Zufallsbytes, nie im Git-Verlauf oder Client-Bundle.
- N4: Kein PII-Feld ist im TypeScript-Typsystem der Event-Properties überhaupt konstruierbar — **und** SDK-seitige IP-/GeoIP-Erfassung ist explizit deaktiviert (§3.2), nicht nur die App-eigenen Felder.

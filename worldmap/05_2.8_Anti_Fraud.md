## 2 — Ziel

Bet-Verhalten, das auf Multi-Accounting oder koordinierten Missbrauch hindeutet, als **read-only Signale** erkennen und in eine **von Menschen geprüfte** Review-Queue stellen — nie automatisch sperren. Löst die in `2.3` (Referral, verworfen) hinterlegte Notiz "Anti-Fraud-Erkennung als eigenständiges, größer angelegtes Thema" ein und schließt die Lücke, dass `risk_events` bisher nur Voucher-Missbrauch abdeckt, nicht das eigentliche Bet-Verhalten.

**Drei Signale (v1):**

1. **Bet-Velocity-Ausreißer** — ungewöhnlich viele Bets pro Zeitfenster für einen einzelnen User.
2. **Multi-Account-Indikator** — mehrere unterschiedliche User-IDs teilen sich denselben (gehashten) Netzwerk-Fingerprint innerhalb eines Zeitfensters.
3. **Win-Rate-Anomalie** — die realisierte Auszahlungsquote (RTP) eines Users in einem Spiel weicht signifikant von der **Kohorten-RTP** (alle Spieler desselben Spiels im selben Fenster) ab.

**Bewusst außerhalb des v1-Scopes:**

- Kein automatisches Sperren/Einfrieren von Accounts — nur Review-Queue.
- Keine theoretische Exact-RTP-Modellierung pro Spiel/Bet-Typ — stattdessen Kohorten-relativer Vergleich (Begründung: Abschnitt 3.4).
- Keine automatische Cron-Ausführung (pg_cron/pg_net) in v1 — Admin löst den Scan manuell per Button aus.
- Kein Client-Device-Fingerprinting (Canvas/WebGL) — nur die serverseitige Request-IP, gehasht.

## 3 — Architektur / Scope

### 3.1 Ist-Zustand (verifiziert durch Codebase-Recherche)

- `wallet_transactions(id, user_id, game, type, amount, balance_after, metadata, created_at)` — `amount` vorzeichenbehaftet (negativ = Bet, positiv = Win), `game` ∈ `{slots, roulette, crash, dice, ...}`. Immutable Audit-Trail, niemals Saldo-Quelle.
- `risk_events` (`029_risk_events.sql`) — bestehende Signal-Senke. `evidence` wird rekursiv redigiert (jeder Key, der auf `secret|token|cookie|password|server_seed|^ip$|device|email|authorization|credential` matcht, wird entfernt). **Rohe IP-Adressen dürfen nie in `evidence` landen — gewollt, wird nicht umgangen.**
- **Kritischer Fund (Security-/Architektur-Review):** `record_risk_event()` validiert `p_signal_type` **zweimal** — einmal über den Table-CHECK, ein zweites Mal hart codiert innerhalb der PL/pgSQL-Funktion selbst (`IF p_signal_type NOT IN ('voucher_velocity', ...) THEN RAISE EXCEPTION`). Eine reine CHECK-Constraint-Erweiterung reicht **nicht** — ohne `CREATE OR REPLACE FUNCTION record_risk_event(...)` mit erweiterter Liste würden `bet_velocity`/`win_rate_anomaly`-Events die Exception auslösen, die `recordRiskEventBestEffort()` fail-open verschluckt (gibt `false` zurück, loggt nur) — **die gesamte Pipeline hätte still nichts geschrieben.**
- **Kritischer Fund (Architektur-/Datenbank-Review):** `getClientIdentifier()` (`request-security.ts:30-35`) liefert bei vorhandener `userId` **`user:<id>`**, nicht die IP — und beide Bet-Routen kennen die `userId` immer. Die ursprüngliche Plan-Annahme, diese Funktion für IP-Extraktion wiederzuverwenden, war falsch und hätte den Multi-Account-Detektor dauerhaft auf 0 Cluster gesetzt (jeder Hash wäre user-eindeutig gewesen).
- `RiskSignalType` (`risk-signals.ts:3-8`) ist ein **geschlossener** TS-Union-Typ — muss additiv erweitert werden, entgegen der Erstfassung dieses Plans, die ihn fälschlich als "bewusst unverändert" auflistete.
- `buildRiskEvent()` hasht das **gesamte** Evidence-Objekt in den Dedup-Fingerprint. Enthält die Evidence volatile Werte (exakte Zähler, exakte Z-Scores), erzeugt jeder erneute Scan eine **neue** Zeile statt den bestehenden Event per `ON CONFLICT` hochzuzählen.
- Admin-API-Pattern (`api/admin/{users,promo-codes,analytics}/route.ts`): `createClient()` → `auth.getUser()` → `isAdminEmail()` (401/403) → `enforceRateLimit()` → `createAdminClient()` → `CasinoLogger.error` bei Fehlern → try/catch → 503. **Schreibende** Routen rufen zusätzlich `validateMutationOrigin()` **zuerst** auf (vor Auth-Check, siehe `promo-codes` POST).
- Next.js 16.3 ist im Projekt aktiv; `after()` aus `next/server` (stable seit Next 15, im Projekt bisher ungenutzt) ist der korrekte Mechanismus für "nach der Antwort, aber garantiert ausgeführt" — ein loses `void promise` kann von der Serverless-Runtime nach dem Response-Flush eingefroren/verworfen werden (Database-Review-Befund).
- Vorhandene pg_cron-/pg_net-Infrastruktur (`027_guide_telemetry_purge_cron.sql`) — Referenzmuster für den Purge-Job dieser Initiative; `024_guide_telemetry_events.sql` zeigt zusätzlich das Muster "führender `created_at`/`occurred_at`-Index für den Purge-Job", das in der Erstfassung dieses Plans fehlte.

_Follow-up, nicht Teil dieser Migration:_ Dies ist die zweite Erweiterung des `signal_type`-Enums. Bei einer dritten Erweiterung lohnt eine Lookup-Tabelle (`risk_signal_types(code TEXT PRIMARY KEY)` + FK) statt eines CHECK-Enums, damit neue Typen ein reines `INSERT` statt DDL sind — für v1 mit zwei Erweiterungen ist der CHECK-Ansatz proportional, kein Refactor jetzt.

**2. Neue Tabelle `bet_network_fingerprints`** — einziger Grund: `risk_events.evidence` darf laut bestehendem Redaktionsdesign nie eine IP enthalten, Multi-Account-Korrelation braucht aber eine abfragbare, userübergreifende Struktur. **Upsert-Design** (nicht eine Zeile pro Bet — Datenbank-Review-Befund: das wäre die Tabelle mit dem höchsten Schreibvolumen im Schema):

```sql
CREATE TABLE IF NOT EXISTS public.bet_network_fingerprints (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id TEXT NOT NULL REFERENCES public.users(id) ON DELETE CASCADE,
  ip_hash TEXT NOT NULL,  -- HMAC-SHA256(ip, FRAUD_FINGERPRINT_SECRET) — nie die rohe IP
  seen_date DATE NOT NULL DEFAULT current_date,
  hit_count INTEGER NOT NULL DEFAULT 1 CHECK (hit_count > 0),
  first_seen_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  last_seen_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  UNIQUE (user_id, ip_hash, seen_date)
);
CREATE INDEX idx_bnf_ip_hash ON public.bet_network_fingerprints(ip_hash, last_seen_at DESC) INCLUDE (user_id);
CREATE INDEX idx_bnf_created_at ON public.bet_network_fingerprints(first_seen_at DESC);  -- führende Spalte für Purge
ALTER TABLE public.bet_network_fingerprints ENABLE ROW LEVEL SECURITY;
REVOKE ALL ON TABLE public.bet_network_fingerprints FROM PUBLIC, anon, authenticated;
-- ENABLE RLS ohne jede Policy = deny-all für anon/authenticated; service_role umgeht RLS
-- rollenbasiert (nicht policy-basiert) — identisches Muster wie risk_events in 029.
```

Ein Upsert pro (User, IP, Tag) statt pro Bet begrenzt die Zeilenzahl auf "aktive User × distincte IPs/Tag" statt "Bets/Tag" — Größenordnungen kleiner, und die Multi-Account-Abfrage wird ein einfaches `GROUP BY ip_hash`.

**3. Zwei read-only SQL-Aggregations-RPCs** (Datenbank-/Architektur-Review-Befund: `COUNT(DISTINCT ...) ... GROUP BY ... HAVING ...` und Kohorten-Mittelwert/-Streuung sind über den Supabase-JS-Query-Builder nicht ausdrückbar, ohne das gesamte Zeitfenster ungefiltert über die Leitung zu ziehen — das wäre kein "TS vs. SQL"-Stilentscheid mehr, sondern ein Performance-/Skalierungsproblem):

```sql
CREATE OR REPLACE FUNCTION public.detect_multi_account_clusters(p_window_hours INT DEFAULT 24, p_min_cluster INT DEFAULT 3)
RETURNS TABLE(ip_hash TEXT, user_ids TEXT[], cluster_size INT)
LANGUAGE sql STABLE SECURITY DEFINER SET search_path = public, pg_temp AS $$
  SELECT ip_hash, array_agg(DISTINCT user_id) AS user_ids, count(DISTINCT user_id)::INT AS cluster_size
  FROM public.bet_network_fingerprints
  WHERE last_seen_at >= now() - (p_window_hours || ' hours')::interval
  GROUP BY ip_hash
  HAVING count(DISTINCT user_id) >= p_min_cluster;
$$;

CREATE OR REPLACE FUNCTION public.compute_cohort_win_rates(p_game TEXT, p_window_hours INT DEFAULT 24, p_min_bets INT DEFAULT 50)
RETURNS TABLE(user_id TEXT, user_rtp NUMERIC, cohort_mean NUMERIC, cohort_stddev NUMERIC, bet_count INT)
LANGUAGE sql STABLE SECURITY DEFINER SET search_path = public, pg_temp AS $$
  WITH per_user AS (
    SELECT user_id,
           sum(amount) FILTER (WHERE type = 'win')::NUMERIC / NULLIF(sum(-amount) FILTER (WHERE type = 'bet'), 0) AS rtp,
           count(*) FILTER (WHERE type = 'bet') AS bets
    FROM public.wallet_transactions
    WHERE game = p_game AND created_at >= now() - (p_window_hours || ' hours')::interval
    GROUP BY user_id
    HAVING count(*) FILTER (WHERE type = 'bet') >= p_min_bets
  )
  SELECT user_id, rtp, avg(rtp) OVER (), stddev_pop(rtp) OVER (), bets
  FROM per_user;
$$;
-- Bet-Velocity bleibt ein einfaches COUNT(*) ... GROUP BY user_id HAVING count(*) >= threshold,
-- ebenfalls als RPC (detect_bet_velocity_outliers), analog strukturiert.

REVOKE ALL ON FUNCTION public.detect_multi_account_clusters(INT, INT) FROM PUBLIC, anon, authenticated;
REVOKE ALL ON FUNCTION public.compute_cohort_win_rates(TEXT, INT, INT) FROM PUBLIC, anon, authenticated;
GRANT EXECUTE ON FUNCTION public.detect_multi_account_clusters(INT, INT) TO service_role;
GRANT EXECUTE ON FUNCTION public.compute_cohort_win_rates(TEXT, INT, INT) TO service_role;
```

TS bleibt zuständig für: Schwellenwert-Vergleich, Severity-Ableitung, Evidence-Bucketing (3.4), Aufruf von `recordRiskEventBestEffort()` — das ist der Teil, der in Vitest ohne echte DB testbar bleibt (RPC-Response gemockt, analog `admin-analytics-route.test.ts`).

**4. Scan-Concurrency-Guard, während Execution nachgeschärft:** Die Erstfassung dieses Plans nannte `pg_try_advisory_lock()`. Bei der Migrationserstellung fiel auf, dass ein **Session-level** Advisory-Lock nicht über mehrere getrennte `.rpc()`-Aufrufe hinweg hält, wenn Supabase-gepoolte Verbindungen keine Session-Persistenz zwischen Requests garantieren — genau dieser Fall liegt hier vor (Lock-Acquire, Scan-Arbeit und Lock-Release sind drei getrennte HTTP-Requests aus derselben Admin-Session, nicht eine einzige SQL-Transaktion). Stattdessen: `fraud_scan_lock`, eine Einzeilen-Tabelle mit atomarem, bedingtem `UPDATE ... WHERE id = true AND (locked_at IS NULL OR gealtert)` — race-sicher pro einzelnem Aufruf (Postgres serialisiert konkurrierende `UPDATE`s auf dieselbe Zeile), unabhängig von Connection-Affinität, mit 5-Minuten-Staleness-Fallback gegen einen abgestürzten Scan. `try_acquire_fraud_scan_lock()`/`release_fraud_scan_lock()`, RLS deny-all wie `risk_events`.

**5. Purge-Job** für `bet_network_fingerprints`, nach dem Muster von `027_guide_telemetry_purge_cron.sql`: `purge_bet_network_fingerprints()` (reine Löschfunktion, isoliert testbar) + `run_bet_fingerprint_purge_job()` (Wrapper mit Alert-on-Failure über dieselbe `cron-alert`-Route), eigener Cron-Job-Name (`bet-fingerprint-purge-daily`, kollidiert nicht mit `guide-telemetry-purge-daily`). Retention: **30 Tage** ab `first_seen_at`.

### 3.4 Fingerprint-Determinismus (Fix für den Dedup-Bug aus 3.1)

`buildRiskEvent()` hasht die gesamte Evidence in den Fingerprint; `record_risk_event()` dedupliziert per `UNIQUE (subject_user_id, fingerprint)`. Damit wiederholte Scans **denselben** Befund als `occurrences++`-Update statt als neue Zeile erfassen, muss die Evidence pro "logischem Fenster" deterministisch sein:

- `windowStart` wird auf den Tagesbeginn (UTC) des Scan-Zeitpunkts **floored**, nicht auf den exakten `now()`-Zeitstempel.
- Exakte Zähler/Z-Scores fließen **nicht roh** in die Evidence — stattdessen gebändert (z. B. Bet-Count in Zehnerschritten, Z-Score gerundet auf 0,5, Cluster-Größe exakt, da klein und stabil genug). Die Severity-Klassifikation selbst (`low`/`medium`/`high`) bleibt die primäre, für Menschen lesbare Information; exakte Rohwerte sind nicht der Punkt eines Dedup-Schlüssels.

### 3.5 Warum Kohorten-relative Win-Rate-Erkennung statt theoretischer RTP

`config.crash.houseEdge` ist die einzige direkt nutzbare Skalar-Konstante; Roulette-Multiplikatoren, Slots-Paytable-Gewichtung und Blackjack sind strategie-/bet-typ-abhängig — eine exakte theoretische Erwartungswert-Formel pro Spiel und Bet-Typ nachzubauen wäre ein eigenständiges, fehleranfälliges Statistik-Projekt. Stattdessen: **Kohorten-Vergleich** über `compute_cohort_win_rates()` (3.3) — spielunabhängig, passt sich automatisch an admin-konfigurierte House-Edge-Änderungen (`game_configs`, Initiative 1.14) an.

### 3.6 Warum kein neuer Money-Pfad-Touch

Die Signal-Berechnung liest ausschließlich historische, bereits abgeschlossene `wallet_transactions`/`bet_network_fingerprints`-Zeilen — nie den laufenden Settlement-Pfad (`settle_game_bet`, `casino-core.ts`). Der einzige Touch-Punkt in bet-nahen Dateien ist ein **einziger, über `after()` entkoppelter Call** pro Route direkt nach dem Rate-Limit-Check (userId + IP dort bereits bekannt, Settlement-Logik unverändert) — kein bestehender Response-Pfad, keine der mehreren Exit-Stellen in `bet/route.ts`/`blackjack/route.ts`, wird angefasst.

## 4 — Anforderungen

### 4.1 Funktional

- F1: `detect_bet_velocity_outliers()`-RPC liefert genau die User, deren Bet-Anzahl im Zeitfenster den konfigurierten Schwellenwert überschreitet.
- F2: `detect_multi_account_clusters()`-RPC liefert genau die `ip_hash`-Cluster mit ≥ 3 unterschiedlichen `user_id` im Zeitfenster; jedes Cluster-Mitglied bekommt einen eigenen `risk_event` mit den übrigen Cluster-Usern als Evidence (max. 10 IDs, mit Zähler bei Überschreitung).
- F3: `compute_cohort_win_rates()`-RPC liefert nur für User mit ≥ 50 Bets im Fenster einen Wert; TS berechnet daraus den Z-Score gegen `cohort_mean`/`cohort_stddev` und erzeugt nur bei Überschreitung eines Schwellenwerts ein Signal.
- F4: Jedes erkannte Signal wird über `recordRiskEventBestEffort()` geschrieben — Fehler beim Schreiben eines einzelnen Signals blockieren nicht die übrigen Signale desselben Scans.
- F5: Wiederholte Scans über dasselbe Fenster erzeugen laut 3.4 `occurrences++` statt neuer Zeilen (Determinismus-Test in `fraud-detection.test.ts`).
- F6: `GET /api/admin/fraud` liefert paginierte, nach Status/Severity/Signal-Typ filterbare `risk_events`.
- F7: `PATCH /api/admin/fraud` prüft `validateMutationOrigin()` **zuerst**, dann Auth, dann `review_risk_event()` mit Pflicht-Begründung.
- F8: `POST /api/admin/fraud/scan` prüft `validateMutationOrigin()` zuerst, nimmt über `try_acquire_fraud_scan_lock()` einen atomaren Row-Lock (kein Session-`pg_advisory_lock` — Supabases gepoolte Verbindungen garantieren keine Session-Persistenz über mehrere getrennte RPC-Aufrufe hinweg, siehe 3.3.4), gibt bei bereits laufendem Scan `409` zurück, gibt sonst eine Zusammenfassung (Anzahl neuer/aktualisierter Signale pro Typ) zurück und gibt den Lock in einem `finally`-Block frei.
- F9: `extractClientIp(request)` liefert die IP unabhängig von `userId` — Verwechslung mit `getClientIdentifier()` wird durch getrennte Funktionen und einen expliziten Test ausgeschlossen.
- F10: Fingerprint-Capture über `after()` hat **keinen** Einfluss auf Statuscode, Latenz oder Payload der bestehenden Bet-/Blackjack-Antwort.

### 4.2 Nicht-funktional

- N1: Kein automatisches Sperren/Einfrieren — `review_risk_event()` ist die einzige Statusänderung, ausschließlich Admin-getriggert.
- N2: **Pseudonymisierung, keine kryptografische Anonymisierung** — HMAC-SHA256(ip, `FRAUD_FINGERPRINT_SECRET`) verhindert, dass jemand _ohne_ das Secret IPs zurückrechnet; jemand _mit_ dem Secret kann den kleinen IPv4-Raum (2³²) brute-forcen. Akzeptiert, weil Secret-Kompromittierung denselben Blast-Radius hat wie eine kompromittierte `SUPABASE_SERVICE_ROLE_KEY` — dokumentiert, nicht als stärkere Garantie verkauft.
- N3: `FRAUD_FINGERPRINT_SECRET` ist server-only, nie im Client-Bundle, 32 Byte Entropie, gleiche Rotations-/Vault-Behandlung wie andere Server-Secrets.
- N4: `bet_network_fingerprints`-Zeilen werden nach 30 Tagen automatisch gelöscht (Purge-Cron, `first_seen_at`-basiert).
- N5: Admin-Routen folgen exakt dem bestehenden Auth/Rate-Limit/Origin-Pattern; GET/PATCH nutzen dieselben Rate-Limit-Bänder wie `promo-codes`/`users` (30/60 Read, 10/60 Write), `/scan` strenger (z. B. 1/300s pro Admin).
- N6: Kein neuer Money-Pfad, keine Änderung an `settle_game_bet`, `game_rounds`-Statuslogik oder Saldo-Berechnung.
- N7: **XFF-Vertrauensgrenze dokumentiert, nicht angenommen** — `extractClientIp()` verlässt sich wie das bestehende Rate-Limiting auf `x-forwarded-for`. Ob die Deployment-Plattform (Vercel, siehe `casino-xi-six.vercel.app` in Migration 027) diesen Header am Edge zuverlässig setzt/überschreibt, wird vor Produktivbetrieb im Security-Review (M12) explizit verifiziert, nicht stillschweigend vorausgesetzt — bis dahin als bekannte Grenze im Risiko-Register (R22) geführt.

Nach Einarbeitung der 15 Review-Befunde nochmals gegen die drei Grundkriterien geprüft:

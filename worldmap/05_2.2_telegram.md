# 05-2.2 Telegram-Benachrichtigungen – Weltklasse-Implementierungsplan

> **Status:** Nullentwurf → wird in derselben Session in Execution überführt (siehe Meilenstein-Tabelle).
> **Abhängigkeiten:** keine. Ersetzt den ursprünglich in `05_ZUKUNFTSPLANUNG.md` (2.2) skizzierten Web-Push-Ansatz vollständig.
> **Sicherheitsgrenze:** Kein Wallet-Schreibpfad, kein Zwei-Wege-Chat, kein Client-Secret. Bot-Token verlässt den Server nie.
> **Nicht im Umfang:** Web Push, voller Telegram-Chatbot (Commands/Balance-Abfrage), Admin-Broadcasts, Outbox-Pattern (siehe Abschnitt „Bewusst abgegrenzt").

**Ziel:** Server-seitige, opt-in Telegram-Benachrichtigung bei Big-Win-Ereignissen (gleiche Schwelle wie die bestehende `BigWinOverlay`-Animation: `multiplier >= 20 || payout >= 500`), über den bereits vorhandenen Bot + Token. Jan verbindet sein Casino-Konto einmalig per Deep-Link mit dem Bot; danach erhält er bei jedem qualifizierenden Win eine Telegram-Nachricht, unabhängig davon, ob der Browser offen ist.

**Entscheidungsverlauf (Kontext):** In der vorausgegangenen Diskussion wurden drei Varianten verglichen (nur Telegram / nur Web Push / kanal-abstrahiert). Telegram wurde gewählt, weil (a) Bot + Token bereits vorhanden sind, (b) Web Push auf iOS Safari die per 1.3 bereits verworfene PWA-Installation voraussetzt, und (c) eine kanal-abstrahierte Architektur für einen einzigen Kanal verfrühte Abstraktion wäre (YAGNI). Details siehe Konversationsverlauf, nicht dupliziert.

## 1 — Bewusst abgegrenzt (Scope-Disziplin)

- **Kein Web Push.** Siehe Entscheidungsverlauf oben.
- **Kein Zwei-Wege-Chat im Bot.** Der Bot verarbeitet ausschließlich `/start <token>` (Linking) und `/stop` (Unlink-Komfortpfad). Jede andere Nachricht erhält eine statische Hinweisantwort, keine Konversationslogik.
- **Kein Outbox-Pattern.** Der Roadmap-Eintrag „Outbox-Pattern für Wallet-Nebenwirkungen" (Phase offen) nennt Notifications explizit als künftigen Konsumenten. V1 hier verzichtet bewusst darauf und dispatcht direkt im Settlement-Response-Pfad (siehe Architekturentscheidung) — der Dispatch ist als eigenständige, reine Funktion geschnitten, damit ein künftiger Outbox-Worker sie später übernehmen kann, ohne dass diese Initiative dafür vorgreifen muss.
- **Keine Admin-Broadcasts.** Nur user-eigene Big-Win-Benachrichtigungen, keine „Nachricht an alle User"-Funktion.
- **Keine Änderung an `BigWinOverlay.tsx` selbst.** Nur die Schwellenwert-Konstante wird in ein gemeinsames Modul extrahiert, damit Client-Overlay und Server-Notifier nicht auseinanderlaufen.

## 2 — Architekturentscheidung

### 2.1 Linking-Flow

1. User klickt in den Einstellungen „Mit Telegram verbinden" → `POST /api/telegram/link` (authentifiziert, rate-limited 5/60s pro User).
2. Server löscht ein eventuell vorhandenes, noch nicht eingelöstes Token desselben Users (max. ein aktiver Flow gleichzeitig) und legt ein neues `telegram_link_tokens`-Token an (UUID v4, 10 Minuten TTL, `service_role`-only).
3. Response liefert den Deep-Link `https://t.me/<BOT_USERNAME>?start=<token>`. `<BOT_USERNAME>` kommt aus `NEXT_PUBLIC_TELEGRAM_BOT_USERNAME` (öffentlich, Bot-Usernamen sind ohnehin öffentlich).
4. User öffnet den Link in Telegram; Telegram schickt automatisch `/start <token>` an den Bot.
5. Telegram ruft (einmalig per `setWebhook` registriert) `POST /api/telegram/webhook` mit dem Update auf, inklusive Header `X-Telegram-Bot-Api-Secret-Token`.
6. Webhook validiert den Secret-Header **zeitkonstant** (`crypto.timingSafeEqual`), parst `/start <token>`, konsumiert das Token atomar (`UPDATE telegram_link_tokens SET consumed_at = now() WHERE token = $1 AND consumed_at IS NULL AND expires_at > now() RETURNING user_id` — eine einzelne atomare `UPDATE … RETURNING`-Anweisung genügt, kein Advisory Lock nötig, da pro Zeile ohnehin nur ein Writer gewinnen kann).
7. Bei Erfolg: `INSERT … ON CONFLICT (user_id) DO UPDATE` in `telegram_links` (chat_id, username, `notifications_enabled = true`, `linked_at = now()`). Ist der `chat_id` bereits mit einem **anderen** `user_id` verknüpft, wird der Link **abgelehnt** (Bot antwortet „Dieser Telegram-Account ist bereits mit einem anderen Casino-Konto verknüpft — dort zuerst trennen."), statt den bestehenden Link stillschweigend zu überschreiben.
8. Bot sendet eine Bestätigungsnachricht. Unlink: `POST /api/telegram/unlink` (authentifiziert) oder `/stop` im Bot als Komfortpfad.

### 2.2 Notification-Dispatch

- Die drei bestehenden Settlement-Punkte — `bet/route.ts` (DICE/SLOTS/ROULETTE-Zweig, `CASHOUT_CRASH`/`RESOLVE_CRASH`-Zweig) und `blackjack/route.ts` (`settled === true`-Zweig) — rufen nach erfolgreicher Settlement-Response `notifyBigWinIfEligible({ userId, game, payout, multiplier, win, replayed })` auf.
- **Bewusst nicht `next/server`'s `after()`**, obwohl das die naheliegende „fire-and-forget nach Response"-API wäre: Das Repo hat für exakt dieses Problem (Nebenwirkung nach Settlement, darf Response nie beeinflussen) mit `guide-telemetry.ts` bereits ein geprüftes, getestetes Muster — `Promise.race` gegen ein Timeout, Fehler abgefangen, Response unverändert. Same-pattern-Wiederverwendung schlägt eine neue, in diesem Repo ungetestete Next-API (siehe „Eigener Plan-Audit" unten für die Abwägung).
- Timeout-Budget: **1200 ms** (nicht 250 ms wie bei der Telemetrie-DB-Schreibung) — ein externer Telegram-API-Call braucht mehr Spielraum als ein DB-Insert; da Big Wins selten sind (Schwelle bewusst hoch), ist die gelegentliche zusätzliche Latenz für den Spieler vertretbar und betrifft nie den Normalfall.
- `settlement.replayed === true` überspringt den Dispatch vollständig — ein Netzwerk-Retry desselben Bets darf nie zwei Telegram-Nachrichten erzeugen.
- Scheitert `sendMessage` mit HTTP 403 (Bot vom Chat blockiert), setzt der Notifier best-effort `notifications_enabled = false` für diesen User (ebenfalls fehler-isoliert) — verhindert wiederholte sinnlose Versuche bei jedem künftigen Big Win.
- Jeder Fehlerpfad wird nur mit einer statischen Lognachricht protokolliert, **nie** mit der zusammengesetzten Telegram-API-URL (die den Bot-Token enthält) oder dem rohen Fetch-Error-Objekt.

## 3 — Verbindliche Daten- und Sicherheitsregeln

- `telegram_links` und `telegram_link_tokens` sind `RLS`-aktiv mit `REVOKE ALL FROM PUBLIC, anon, authenticated` — Client liest/schreibt nie direkt, ausschließlich über die fünf API-Routen mit `service_role` (konsistent mit `guide_telemetry_events`/`promo_code_redemptions`, nicht mit dem älteren direkten-RLS-Read-Muster von `users`).
- `chat_id` ist `BIGINT`, nicht `INTEGER` — Telegrams `chat_id` kann bis zu 52 Bit signed umfassen.
- Der Webhook-Secret-Header-Vergleich ist zeitkonstant (`crypto.timingSafeEqual` auf gleich lange Puffer, sonst sofortiger 401 ohne Vergleich).
- Link-Tokens sind UUID v4, 10 Minuten gültig, einmal verwendbar, nie geloggt.
- Der Bot-Token steht ausschließlich in `TELEGRAM_BOT_TOKEN` (server-only, nie `NEXT_PUBLIC_*`). Nur der Bot-**Username** ist öffentlich.
- Die Webhook-Route ist von der Origin-Prüfung ausgenommen (Telegram sendet keinen Browser-Origin-Header) — exakt das bestehende `/api/webhooks/clerk`-Muster in `src/proxy.ts`, keine neue Ausnahme-Klasse.
- Alle vier authentifizierten Mutation-Routen (`link`, `unlink`, `toggle`) validieren Origin **vor** Body-Parsing (bestehendes `validateMutationOrigin`-Muster) und sind rate-limited.
- Die Telegram-Nachricht selbst enthält nur, was der Spieler im eigenen `BigWinOverlay` ohnehin sieht: Spiel, Multiplikator, Gewinnbetrag. Kein Gesamt-Balance, keine anderen Nutzerdaten.

## 4 — Drei-Perspektiven-Prüfung

### Perspektive Security-Auditor

| Risiko                                                                                   | Mitigation                                                                                 |
| ---------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| Webhook-Spoofing (Angreifer ruft die Route ohne echten Telegram-Ursprung auf)            | Secret-Token-Header, zeitkonstanter Vergleich, 401 ohne Detail bei Mismatch                |
| Race Condition bei doppelter Token-Einlösung (Telegram-Retry bei Timeout)                | Einzelne atomare `UPDATE … WHERE consumed_at IS NULL RETURNING`                            |
| Token-Errraten/Brute-Force                                                               | UUID v4 (122 Bit Entropie), 10-Minuten-TTL, einmalig verwendbar                            |
| Chat-ID-Übernahme (ein bereits verlinkter Telegram-Account wird versehentlich umgehängt) | `ON CONFLICT (chat_id)` wird abgelehnt statt überschrieben, siehe 2.1 Schritt 7            |
| IDOR bei Unlink/Toggle                                                                   | Routen leiten `user_id` ausschließlich aus der Server-Session ab, nie aus dem Request-Body |
| Bot-Token-Leak über Logs                                                                 | Nie die zusammengesetzte API-URL oder rohe Fetch-Errors loggen, nur statische Meldungen    |
| Missbrauch der Link-Route (Token-Flooding)                                               | Rate-Limit 5/60s pro User; ein neues Token ersetzt automatisch ein noch offenes            |

### Perspektive Reliability / Money-Path

- Dispatch liest ausschließlich das bereits committete Settlement-Ergebnis — keine Rückwirkung auf die Wallet-Transaktion, kein zusätzlicher DB-Schreibzugriff im kritischen Pfad.
- Timeout-Race stellt sicher, dass ein hängender Telegram-Call die Bet-Response nie über 1200 ms hinaus verzögert; die Response selbst (Status, Body) ist zum Zeitpunkt des Dispatch-Aufrufs bereits vollständig bestimmt und wird durch dessen Ausgang nicht mehr verändert.
- `replayed`-Flag verhindert Doppel-Benachrichtigung bei Client-seitigen Retries — dieselbe Idempotenz-Garantie, die die Settlement-RPCs selbst schon für die Wallet bieten, wird eins zu eins auf die Notification übertragen.
- Kein neuer Money-Pfad: Der Notifier hat keinerlei Schreibzugriff auf `users`/`wallet_transactions`.

### Perspektive UX/Produkt

- Verlinken = Opt-in (kein separater Doppel-Opt-in nötig), aber ein Mute-Toggle erlaubt Pausieren ohne vollständiges Trennen.
- Fehlt `TELEGRAM_BOT_TOKEN`/`NEXT_PUBLIC_TELEGRAM_BOT_USERNAME` (Jan hat es noch nicht gesetzt), liefert `/api/telegram/status` `configured: false`; die UI zeigt einen klaren „noch nicht verfügbar"-Zustand statt eines kaputten Buttons — gleiches Degradierungs-Muster wie 2.7s `guide.status = 'unavailable'`.
- Automatisches Deaktivieren bei Bot-Block (403) verhindert, dass der User in den Einstellungen fälschlich „verbunden" sieht, obwohl keine Nachricht mehr ankommt — ohne diese Erkennung würde der Status stillschweigend veralten.
- Jede unbekannte Bot-Nachricht bekommt eine einzelne statische Hinweisantwort statt Stille oder eines Fehlers — kleine UX-Politur, kein Scope-Creep (ein String, keine Konversationslogik).

## 5 — Datenmodell (Migration `025_telegram_link_notifications.sql`)

- **`telegram_links`**: `user_id TEXT PRIMARY KEY REFERENCES public.users(id) ON DELETE CASCADE`, `chat_id BIGINT NOT NULL UNIQUE`, `telegram_username TEXT NULL`, `notifications_enabled BOOLEAN NOT NULL DEFAULT true`, `linked_at TIMESTAMPTZ NOT NULL DEFAULT now()`.
- **`telegram_link_tokens`**: `token UUID PRIMARY KEY DEFAULT gen_random_uuid()`, `user_id TEXT NOT NULL REFERENCES public.users(id) ON DELETE CASCADE`, `created_at TIMESTAMPTZ NOT NULL DEFAULT now()`, `expires_at TIMESTAMPTZ NOT NULL DEFAULT now() + interval '10 minutes'`, `consumed_at TIMESTAMPTZ NULL`.
- Beide Tabellen: `ENABLE ROW LEVEL SECURITY`, `REVOKE ALL ... FROM PUBLIC, anon, authenticated`. Kein direkter Client-Zugriff, siehe Abschnitt 3.
- `purge_expired_telegram_link_tokens()`: `SECURITY DEFINER`-Funktion, löscht Tokens älter als 1 Tag (abgelaufen oder eingelöst) — analog `purge_guide_telemetry_events()`. Täglicher Executor ist ein Go-live-Gate (Abschnitt 9), identisch zum bereits offenen Gate aus 2.7.
- Kein `ON DELETE`-Sonderfall nötig: Löscht `public.users` einen User, kaskadieren beide Tabellen automatisch — kein separater Erasure-Pfad wie bei 2.7 nötig, da hier eine echte FK-Beziehung besteht statt pseudonymer Hashes.

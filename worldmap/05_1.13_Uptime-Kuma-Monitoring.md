## 5 — Architektur (finaler Stand nach Review + Execution)

### 5.1 Health-Route (`src/app/api/health/route.ts`) — ✅ implementiert, verifiziert

- `GET`-Handler, liefert `{ status, timestamp, commit, deploymentId }`, HTTP 200 im Normalzustand.
- `export const dynamic = 'force-dynamic'` + `Cache-Control: no-store` — empirisch verifiziert gegen Production: zwei aufeinanderfolgende Calls liefern unterschiedliche `timestamp`-Werte, `X-Vercel-Cache: MISS` (Abschnitt 11).
- `commit`/`deploymentId` aus `VERCEL_GIT_COMMIT_SHA`/`VERCEL_DEPLOYMENT_ID` (Vercel-eigene automatische Env-Vars, keine Secrets) — Architektur-Review-Befund A2: verhindert, dass ein fehlgeschlagener Build unbemerkt bleibt, weil der Alias weiter die letzte erfolgreiche Antwort liefert.
- **In-Memory-Rate-Limit** (120 Requests/Min pro Identifier, fail-open bei internem Fehler) statt des geteilten Upstash-Limiters — Security-Review-Befund 2 (Denial-of-Wallet-Kostenrisiko durch `force-dynamic` + `no-store`, das den CDN-Schutz gerade abschaltet) **und** eigene Erkenntnis, dass der Upstash-Limiter fail-**closed** ist (`src/lib/security/request-security.ts`) — das hätte die Liveness-Route bei einem Upstash-Ausfall fälschlich „down" melden lassen. Beides zusammen ergibt die In-Memory-Lösung.
- **`HEALTH_FORCE_FAIL`-Chaos-Schalter** (503, wenn `'1'`) für den Incident-Test — ersetzt die ursprünglich geplanten Break/Revert-Commits (Architektur-Review-Befund A6).
- Kein Supabase-/Upstash-Import, kein `process.env.*SUPABASE*`/`*UPSTASH*`-Read — durch Source-Scan-Test erzwungen (`health-route.test.ts`).

### 5.2 Middleware-Bypass (`src/proxy.ts`) — ✅ implementiert, verifiziert

- **Nicht** über `PUBLIC_ROUTES` gelöst (das war der ursprüngliche Plan) — Architektur-Review-Befund A7 zeigte, dass `PUBLIC_ROUTES` nur den Sign-in-Redirect unterdrückt, aber `createServerClient`+`getUser()` trotzdem für jeden Request läuft. Bei falsch konfiguriertem Supabase-Env auf `staging` hätte das die Health-Route permanent mit `500 "Security boundary unavailable"` beantwortet — genau der falsche Fehlalarm, den die Route verhindern soll.
- **Fix:** `pathname === '/api/health'` wird jetzt ganz am Anfang von `proxy()` geprüft, vor der Supabase-Client-Erstellung — einzige Quelle der Wahrheit für den Public-Status dieser Route (bewusst nicht zusätzlich in `PUBLIC_ROUTES`, um Doppel-Deklaration zu vermeiden). Per Source-Order-Test erzwungen (`proxy-health-bypass.test.ts`).
- **Zusätzlich:** hartes technisches Mutations-Verbot für `staging` — jeder nicht-GET/HEAD/OPTIONS-Call auf `/api/*` bekommt `503`, wenn `process.env.VERCEL_GIT_COMMIT_REF === 'staging'` (Vercels automatische Env-Var, nichts manuell zu konfigurieren). Security-Review-Befund 3: `staging` teilt sich die produktive Supabase-Instanz, R5 war zuvor nur dokumentarisch abgesichert.

### 5.3 Staging-Ziel = Vercel-Branch-Deployment — ⚠️ teilweise blockiert, siehe 5.3a

- `staging`-Branch existiert auf GitHub (per GitHub Action erzeugt, siehe 5.7a) und zeigt exakt auf denselben Commit wie `main`.
- **Bewusste Grenze:** Dieser Branch dient ausschließlich als Health-Check-Ziel, teilt sich weiterhin die produktive Supabase-Instanz (siehe 5.2 für die technische Absicherung dagegen).

### 5.3a — Zwei empirisch gefundene Blocker (nicht im Ursprungsplan)

Beide während der eigenen Execution-Prüfung entdeckt, nicht vom Multi-Perspektiven-Review vorhergesagt (Review fand das SSO-Risiko konzeptionell, Abschnitt 9 Architektur-Befund A3 — die zweite Lücke kam erst beim tatsächlichen Testen ans Licht):

1. **Vercel Authentication (SSO-Gate) auf Preview-URLs.** Bestätigt per `mcp__vercel__get_project_deployment_protection`: `ssoProtection.enabled: true, deploymentType: "all_except_custom_domains"`. Empirisch verifiziert: `casino-xi-six.vercel.app` (Produktions-Alias) → `200`, aber jede Hash-/Branch-Alias-Preview-URL (getestet: `casino-75cjxj0eq-...vercel.app`, `casino-git-main-...vercel.app`) → `302` zur Vercel-Login-Seite. Ein „Trusted IPs"-Bypass für die VPS-IP wurde versucht (`update_project_deployment_protection`) und von der API mit `invalid_billing_plan` abgelehnt — **Trusted IPs ist ein Pro-Feature, auf dem Hobby-Plan nicht verfügbar.** Ich habe die SSO-Einstellung selbst **nicht** deaktiviert (wäre eine projektweite Sicherheitsänderung mit Wirkung auf alle Preview-Deployments, nicht nur auf diese eine Initiative — außerhalb dessen, was ich ohne Rücksprache ändern sollte).
2. **Der reine Branch-Push auf `staging` hat keinen Vercel-Build ausgelöst.** GitHub Deployments API (`/repos/ameisw667/Casino/deployments?ref=staging`) liefert `[]` — Vercels GitHub-App hat den Push nicht einmal registriert. Alle bisherigen Nicht-Produktions-Deployments dieses Projekts (siehe `list_deployments`) haben durchgehend eine verknüpfte Pull-Request-ID; ein reiner Branch-Push ohne PR ist damit ein bisher ungetesteter Fall. `curl` gegen die Branch-Alias-URL liefert `404 DEPLOYMENT_NOT_FOUND`. Ich konnte das nicht selbst reparieren: kein `vercel.json`/`ignoreCommand` im Repo (ausgeschlossen), keine `gh`-CLI und kein GitHub-API-Token in dieser Umgebung, um testweise eine PR zu öffnen.

**Fix für beide, Jans Aktion (siehe Abschnitt 12):** In Vercel-Dashboard → Projekt `casino` → Settings → Git → prüfen, ob „Preview Deployments" auf alle Branches oder nur auf PRs beschränkt ist (Punkt 2) → ggf. umstellen oder eine PR offen halten. Für Punkt 1: Settings → Deployment Protection → „Protection Bypass for Automation" aktivieren, das generierte Secret dem Kuma-Staging-Monitor als Custom-Header `x-vercel-protection-bypass: <secret>` mitgeben (Standard-Vercel-Mechanismus für genau diesen Automatisierungs-Anwendungsfall, Hobby-Plan-tauglich).

### 5.4 Kuma-Host = bestehende VPS (Docker, self-hosted) — ✅ Skript fertig

- `scripts/monitoring/setup-kuma-vps.sh`, gebaut nach dem bestätigten `setup-vps.sh`-Muster.
- **Sicherheits-Fix nach Review (Security-Befund 4):** nginx-Aktivierung (= öffentliche Erreichbarkeit) läuft jetzt **nach** der Bestätigung, dass der Kuma-Erstsetup-Assistent bereits abgeschlossen ist — vorher lag die Reihenfolge falsch herum (nginx zuerst, Erinnerung erst danach), was ein reales Zeitfenster für den bekannten unauthenticated-Setup-Exploit (CVE-2023-38646) offen gelassen hätte.
- **Ausführung ist Jans manuelle Aktion** (kein SSH-Zugriff von hier).

### 5.5 Monitore in Kuma

- **„Staging"** → `https://casino-git-staging-....vercel.app/api/health`, HTTP(s)-Keyword-Check, Custom-Header `x-vercel-protection-bypass` (siehe 5.3a), **Retries ≥ 2 vor Alarm** (Architektur-Review-Befund A5 — ein einzelner Prüfstandort/VPS kann selbst kurz hängen, das darf nicht sofort einen Fehlalarm auslösen). Einziges Ziel des Incident-Tests.
- **„Production"** → `https://casino-xi-six.vercel.app/api/health`, rein passiv, gleiche Retry-Einstellung. Nie absichtliches Ausfallziel.

### 5.6 Benachrichtigung — ⚠️ Plan geändert nach Security-Review

- **Nicht** der bestehende Spieler-Bot (`CASINO_VIBE_CODING_JANbot`) — Security-Review-Befund 1: Ein Telegram-Bot hat nur ein aktives Webhook-Ziel, gesteuert einzig durch den Token. Würde der Token (der laut ursprünglichem Plan auf der VPS landen sollte — einem zweiten, schwächer gehärteten Host als Vercel) dort kompromittiert, könnte ein Angreifer mit demselben Token `/api/telegram/webhook` (den produktiven Linking-/Big-Win-Pfad) kapern oder lahmlegen.
- **Stattdessen:** neuer, dedizierter Bot über BotFather (Jans eigener Telegram-Account, < 1 Minute, kein neues externes Konto im Sinne der Kontoerstellungs-Grenze — es ist Jans bestehender Telegram-Zugang). Reduziert den Blast-Radius eines VPS-Kompromisses auf den Ops-Kanal, ohne den Geld-Bot zu berühren.
- Bot-Erstellung + Chat-ID-Beschaffung sind Jans Aktion (Abschnitt 12).

### 5.7 Incident-Test-Ablauf (Runbook)

1. Kuma zeigt beide Monitore „Up".
2. `HEALTH_FORCE_FAIL=1` auf der `staging`-Umgebung in Vercel setzen (Dashboard → Environment Variables → nur `staging`-Branch-Scope) statt eines Break-Commits.
3. Kuma erkennt „Down" nach den konfigurierten Retries, Telegram-Alarm trifft ein — Zeitstempel notieren.
4. Ursache bestätigen (erwartet).
5. `HEALTH_FORCE_FAIL` wieder entfernen.
6. Kuma erkennt „Up", zweiter Telegram-Alarm (Recovery) — erst dieser schließt den Test ab (R9).
7. Post-Mortem-Notiz: Ursache, Erkennungsdauer, betroffene Nutzer (keine), Lessons Learned.

### 5.7a Staging-Branch-Pflege — ✅ automatisiert

- `.github/workflows/staging-mirror.yml`: bei jedem Push auf `main` wird `staging` per `git push origin HEAD:refs/heads/staging --force-with-lease` exakt auf denselben Stand gebracht. Läuft bereits erfolgreich (GitHub-Actions-Run bestätigt, `conclusion: success`).
- **Bewusste Grenze:** verhindert Drift (Architektur-Review-Befund A6) — niemand committet manuell auf `staging`, der Incident-Test läuft über den Env-Var-Schalter (5.7), nicht über Commits.

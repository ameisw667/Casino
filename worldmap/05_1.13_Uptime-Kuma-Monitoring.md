## 2 — Was tatsächlich noch im Code steckt (`src/app/api/health/route.ts`)

- `GET`-Handler, liefert `{ status, timestamp, commit, deploymentId }`, HTTP 200 im Normalzustand.
- `force-dynamic` + `Cache-Control: no-store` — kein Caching, jeder Call ist live. Verifiziert gegen Production: zwei Calls im Abstand von 2s liefern unterschiedliche `timestamp`-Werte, `X-Vercel-Cache: MISS`.
- `commit`/`deploymentId` aus Vercels automatischen Env-Vars — zeigt, ob wirklich der aktuelle Build antwortet (nicht ein alter, bei dem der letzte Deploy fehlgeschlagen ist).
- In-Memory-Rate-Limit (120 Requests/Min, fail-open) — verhindert Missbrauch, ohne von Upstash abhängig zu sein (der geteilte Rate-Limiter würde bei Upstash-Ausfall fälschlich „down" melden).
- `HEALTH_FORCE_FAIL`-Umgebungsvariable: setzt man sie auf `'1'`, liefert die Route `503` statt `200` — **ungefährlich**, betrifft nur diese eine Route, keine echte Spiel-/Wallet-Funktion. Damit lässt sich der Alarm-Weg testen, ohne echten Ausfall zu produzieren (siehe Abschnitt 4).
- Middleware-Bypass in `src/proxy.ts`: Health-Route wird geprüft, bevor der Supabase-Client überhaupt erstellt wird — ein Supabase-Problem kann die Liveness-Route nicht fälschlich „down" erscheinen lassen.
- Keine Datenbank-, Wallet- oder Secret-Berührung — per Source-Scan-Test erzwungen.

**Live-URL:** `https://casino-xi-six.vercel.app/api/health`

## 4 — Ein Testlauf (optional, wenn du den Alarm einmal live sehen willst)

1. Vercel-Dashboard → Projekt `casino` → Settings → Environment Variables → `HEALTH_FORCE_FAIL=1` setzen (Production).
2. Redeploy abwarten (oder Vercel triggert automatisch bei Env-Var-Änderung, je nach Einstellung — sonst einmal „Redeploy" klicken).
3. Warten, bis der Checker den nächsten Check macht → E-Mail-Alarm sollte kommen.
4. `HEALTH_FORCE_FAIL` wieder entfernen, redeployen, Recovery-Mail abwarten.

Während des ganzen Tests bleibt das eigentliche Casino voll funktionsfähig — nur `/api/health` meldet kurz „down".

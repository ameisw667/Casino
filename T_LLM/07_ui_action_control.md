## 3 — Verifizierter Ist-Stand (2026-09-06, vor dieser Härtung)

`CasinoGuidePanel.tsx` Zeilen 144–159 (vor L1):

```ts
const handleActionClick = (action: { type: string; target?: string; label: string }) => {
  if (action.type === 'open_vault') {
    router.push('/vault');
  } else if (action.type === 'open_history') {
    router.push('/history');
  } else if (action.type === 'open_leaderboard') {
    router.push('/leaderboard');
  } else if (action.type === 'open_settings') {
    router.push('/vault');
  } else if (action.type === 'open_rank_benefits') {
    router.push('/vault');
  } else if (action.type === 'navigate_game' && action.target) {
    const cleanTarget = action.target.toLowerCase().replace(/[^a-z0-9]/g, '');
    router.push(`/games/${cleanTarget}`);
  }
};
```

`guide-tools.ts`s `UI_ACTION_TARGETS` (siehe [`01_function_calling.md`](01_function_calling.md) §3, aus derselben Codebasis) listet 10 Werte, von denen nur 5 (`blackjack`, `crash`, `dice`, `roulette`, `slots`) reale `/games/<slug>`-Routen sind. Der `navigate_game`-Zweig oben prüfte `action.target` nur auf `truthy` und alphanumerische Zeichen — nicht darauf, ob der bereinigte Wert tatsächlich einer der 5 Spiele ist. Ein vom Modell gesendetes `{ action: 'navigate_game', target: 'vault' }` (technisch server-valide, da `'vault'` in `UI_ACTION_TARGETS` enthalten ist) hätte den Spieler auf die nicht existierende Route `/games/vault` geschickt.

Es existierte keine Testdatei für `CasinoGuidePanel.tsx` im gesamten Repository — die Routing-Entscheidung war weder isoliert testbar noch getestet.

**Verifizierter Ist-Stand (2026-09-07, vor L2):** `answer.ts`s Tool-Call-Schleife (Zeilen ~85–99, vor L2):

```ts
for (const call of functionCalls) {
  toolInputs.push({
    type: 'function_call',
    call_id: call.callId,
    name: call.name,
    arguments: call.rawArguments,
  });
  const toolResult = await executeGuideTool(call.name, call.arguments, userId);
  toolInputs.push({
    type: 'function_call_output',
    call_id: call.callId,
    output: JSON.stringify(toolResult),
  });
}
```

`toolResult` (für `trigger_ui_action` das sanitierte `{ success, action, target, label }` aus `sanitizeUiAction()`) fließt ausschließlich in `toolInputs` — also nur in den **nächsten OpenAI-Request** (Turn 2) — nie in den `GuideAnswerResult`, den die Funktion selbst zurückgibt. Beide `return`-Statements der Funktion (Turn-2-Erfolg und der abschließende Fallback) setzten vor L2 kein `action`-Feld, obwohl `GuideAnswerResult` (`types.ts`) es deklariert. `route.ts`s Nicht-Streaming-Zweig (`shouldStream === false`, z. B. bei explizitem `stream: false` im Request-Body) gab zusätzlich nur `{ answer: answerResult.answer, contextVersion }` zurück — selbst ein nachträglich befülltes `answerResult.action` hätte diesen zweiten Filter noch passieren müssen. `useGuideChatStream.ts`s „Classic JSON fallback"-Zweig liest `action` bereits aus der Response (`'action' in payload ? ... : undefined`), was zeigt, dass der Client-Contract dieses Feld längst erwartet — nur der Server lieferte es nie. Kein bestehender Test in `chat-guide.test.ts` prüfte `result.action` für einen `trigger_ui_action`-Tool-Call.

## 4 — Meilensteine

### L1 — `navigate_game` gegen echte Spiel-Slugs validieren ✅ ausgeführt (2026-09-06)

- **Ziel:** Die in §2 #6/#7 benannte Lücke schließen — `navigate_game` darf nur noch zu einer der 5 echten Spiel-Routen führen; jede andere Kombination wird zu einem No-Op statt zu einer toten Route.
- **Umsetzung:** Neue exportierte, reine Funktion `resolveGuideActionRoute(action)` in `guide-config.ts` zentralisiert die gesamte Routing-Entscheidung (inkl. der bereits bestehenden 5 Nicht-Spiel-Fälle, unverändert übernommen) und führt für `navigate_game` zusätzlich eine `GUIDE_ACTION_GAME_TARGETS`-Allowlist-Prüfung (`['blackjack', 'crash', 'dice', 'roulette', 'slots']`) nach der bestehenden Zeichen-Sanitierung ein — nur bei einem Treffer wird eine Route zurückgegeben, sonst `null` (No-Op, konsistent mit dem bereits etablierten Verhalten für unbekannte `action.type`-Werte). `CasinoGuidePanel.tsx`s `handleActionClick` ruft jetzt nur noch `resolveGuideActionRoute(action)` auf und navigiert bei einem Treffer.
- **Neue Tests:** `guide-config.test.ts` (neue Datei) — 5 Tests: alle 5 Nicht-Spiel-Routen unverändert, alle 5 echten Spiel-Targets korrekt geroutet, Sanitierung eines gemischten/interpunktierten Targets, **Regressionstest für den konkreten Fund** (`navigate_game` mit `target: 'vault'`/`'settings'`/`javascript:alert(1)` liefert `null` statt einer toten oder gefährlichen Route), sowie No-Op bei fehlendem Target/unbekanntem Typ.
- **Verifizierung (2026-09-06):** `npm run typecheck` 0 Fehler · `npm run test` 1630/1630 grün (215 Dateien, +1 neue Testdatei mit 5 Tests) · `npm run lint` 0 Fehler (23 vorbestehende Warnungen, keine in den geänderten/neuen Dateien) · `npm run build` erfolgreich (nach Bereinigung eines veralteten `.next`-Cache-Artefakts, wie bereits in vorherigen Härtungen dieser Konversation dokumentiert) · `git status --short` zeigt nur `src/components/social/CasinoGuidePanel.tsx` (M), `src/components/social/casino-guide/guide-config.ts` (M) + die neue Datei `guide-config.test.ts`.

### L2 — `trigger_ui_action`-Ergebnis im Nicht-Streaming-Antwortpfad ausliefern ✅ ausgeführt (2026-09-07)

- **Ziel:** Die in §2 #11 / §3 (L2-Abschnitt) benannte Lücke schließen — ein vom Modell im Nicht-Streaming-Pfad ausgelöster `trigger_ui_action`-Aufruf muss tatsächlich in der API-Response ankommen, statt lautlos zwischen Turn 1 und Turn 2 verloren zu gehen.
- **Umsetzung:**
  - `answer.ts`: Eine neue, auf Funktionsebene deklarierte Variable `uiAction: GuideAnswerResult['action']` wird in der Tool-Call-Schleife gesetzt, sobald `call.name === 'trigger_ui_action'` — aus `toolResult` (dem bereits sanitierten `executeGuideTool()`-Ergebnis, **nicht** aus den rohen Modell-Argumenten) via sicherer `typeof`-Narrowing (kein `any`-Cast). Beide `return`-Statements der Funktion (Turn-2-Erfolg und der abschließende Fallback) setzen jetzt `action: uiAction`.
  - `route.ts`: Der Nicht-Streaming-Zweig gibt jetzt `{ answer: answerResult.answer, action: answerResult.action, contextVersion }` zurück statt das Feld zu verschlucken. Da `apiSuccessResponse()` intern `JSON.stringify` nutzt, bleibt die Response-Form für Fälle ohne Action (`action: undefined`) byteidentisch zum vorherigen Verhalten — kein bestehender Test musste wegen eines neu erscheinenden Feldes angepasst werden.
- **Neue Tests:** `chat-guide.test.ts` — Regressionstest, der einen `trigger_ui_action`-Funktionsaufruf mit bewusst bösartigen/übergroßen Roh-Argumenten simuliert (`target: 'javascript:alert(1)'`, ein 130 Zeichen langes `label`) und prüft, dass `result.action` das **sanitierte** Ergebnis trägt (Target verworfen, Label auf 60 Zeichen gekappt) statt der rohen Modell-Eingabe. `chat-guide-route.test.ts` — Regressionstest, der `requestCasinoGuideAnswer` mit einem `action`-Feld mockt und prüft, dass die vollständige JSON-Response dieses Feld unverändert enthält.
- **Verifizierung (2026-09-07):** `npm run typecheck` 0 Fehler · `npm run test` 1662/1662 grün (217 Dateien, +2 neue Tests) · `npm run lint` 0 Fehler (30 Warnungen gesamt, keine in den 4 geänderten Dateien) · `npm run build` erfolgreich · `git status --short` zeigt nur `src/lib/casino/chat-guide/answer.ts` (M), `src/app/api/chat/bot-response/route.ts` (M), `src/lib/casino/__tests__/chat-guide.test.ts` (M), `src/lib/security/__tests__/chat-guide-route.test.ts` (M).

## 5 — Definition of Done

1. `navigate_game` führt ausschließlich zu einer der 5 echten `/games/<slug>`-Routen; jede andere Zielangabe ist ein No-Op. _(L1)_
2. Alle 5 bereits bestehenden Nicht-Spiel-Routing-Fälle bleiben byteidentisch zum vorherigen Verhalten. _(L1)_
3. Die gesamte Routing-Entscheidung ist als reine, unit-testbare Funktion isoliert, ohne eine neue Test-Abhängigkeit einzuführen. _(L1)_
4. Der Fix ist durch 5 dedizierte, deterministische Unit-Tests regressionsgesichert. _(L1)_
5. Ein `trigger_ui_action`-Tool-Call landet im Nicht-Streaming-Pfad auf `GuideAnswerResult.action` — auf jedem Return-Pfad der Funktion, nicht nur dem Turn-2-Erfolgsfall. _(L2)_
6. Das ausgelieferte `action`-Objekt ist immer das sanitierte `executeGuideTool()`-Ergebnis, nie die rohen Modell-Argumente. _(L2)_
7. `route.ts` leitet `answerResult.action` unverändert in die JSON-API-Response weiter; die Response-Form für Antworten ohne Action bleibt unverändert. _(L2)_

## 3 — Verifizierter Ist-Stand (2026-09-06, vor dieser Härtung)

`voice-transcribe/route.ts` Zeile 183 (vor L1): `CasinoLogger.error('VoiceTranscribe', error instanceof Error ? error.message : 'Unknown error');` — nur 2 Argumente. `voice-synthesize/route.ts` Zeile 192 (vor L1): identisches Muster mit `'VoiceSynthesize'`. Beide übergeben den extrahierten `.message`-String als zweiten Parameter (`message`), das dritte Argument (`error`) blieb `undefined`.

`CasinoLogger.error(module, message, error?, requestId?)` in [`src/lib/casino/logger.ts:32-46`](../src/lib/casino/logger.ts) verzweigt intern: `if (error instanceof Error) { Sentry.captureException(error, ...) } else { Sentry.captureMessage(message, ...) }`. Mit `error === undefined` griff in beiden Routen immer der `captureMessage`-Zweig — jeder Absturz wurde in Sentry nur als Text-Message ohne Stacktrace und ohne Exception-Fingerprint-Gruppierung erfasst.

Ein Grep über alle `CasinoLogger.error`-Aufrufe unter `src/app/api/chat/` bestätigte: `bot-response/route.ts`, `chat/route.ts` und `chat/feedback/route.ts` übergeben durchgehend das echte `Error`-Objekt als drittes Argument (z. B. `CasinoLogger.error('API/Chat/Feedback', 'Feedback route threw', err instanceof Error ? err : undefined);`) — nur die beiden Voice-Routen wichen davon ab.

## 4 — Meilensteine

### L1 — `CasinoLogger.error`-Aufrufkonvention in beiden Voice-Routen korrigieren ✅ ausgeführt (2026-09-06)

- **Ziel:** Die in §2 #6/#7/#9 benannte Lücke schließen — beide äußeren `catch`-Blöcke übergeben jetzt eine statische, beschreibende Message als zweites Argument und das tatsächliche `Error`-Objekt als drittes Argument, damit Sentry `captureException` statt `captureMessage` verwendet.
- **Umsetzung:** `voice-transcribe/route.ts` — `CasinoLogger.error('VoiceTranscribe', 'Voice transcription request failed', error instanceof Error ? error : undefined)`. `voice-synthesize/route.ts` — `CasinoLogger.error('VoiceSynthesize', 'Voice synthesis request failed', error instanceof Error ? error : undefined)`. Kein Verhalten für den Client geändert — beide Routen antworten weiterhin mit derselben generischen `500`-Nachricht (`SERVICE_UNAVAILABLE`).
- **Neue Tests:** `voice-routes.test.ts` — je 1 Test pro Route („logs the actual exception object instead of just its message, so Sentry keeps the stack trace"), die `enforceRateLimit` einen echten Error werfen lässt (erreicht zuverlässig den äußeren `catch`-Block) und prüft, dass `CasinoLogger.error` mit `(module, expect.any(String), expect.any(Error))` aufgerufen wird.
- **Verifizierung (2026-09-06):** `npm run typecheck` 0 Fehler · `npm run test` 1622/1622 grün (214 Dateien, +2 neue Tests) · `npm run lint` 0 Fehler (23 Warnungen — die eine zusätzliche gegenüber der vorherigen Härtung liegt in einer unberührten `scripts/`-Datei, bestätigt nicht mit dieser Änderung zusammenhängend) · `npm run build` erfolgreich (nach Bereinigung eines veralteten `.next`-Cache-Artefakts, das erneut mit dieser Änderung nichts zu tun hatte — Clean-Rebuild bestätigt, siehe auch [`04_token_streaming.md`](04_token_streaming.md) für denselben Umgebungs-Effekt) · `git status --short` zeigt nur `src/app/api/chat/voice-transcribe/route.ts` (M), `src/app/api/chat/voice-synthesize/route.ts` (M) + `src/lib/security/__tests__/voice-routes.test.ts` (M).

## 5 — Definition of Done

1. Beide äußeren `catch`-Blöcke übergeben bei einem echten `Error`-Objekt dieses Objekt als drittes Argument an `CasinoLogger.error`.
2. Sentry erfasst künftige Abstürze in diesen beiden Routen mit vollem Stacktrace und korrekter Exception-Gruppierung statt als Text-Message.
3. Der Client-Response-Vertrag bleibt für beide Routen unverändert (generische `500`-Nachricht, kein Detail-Leak).
4. Beide Fixes sind durch dedizierte, deterministische Unit-Tests regressionsgesichert (kein Live-OpenAI-/Sentry-Aufruf nötig).

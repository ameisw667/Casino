## 3 — Verifizierter Ist-Stand (2026-09-06, vor dieser Härtung)

`suggestions.ts`s `SuggestionStreamFilter.flush()` (vor L1):

```ts
flush(): { textToEmit: string; suggestionsFound: string[] | null } {
  if (this.isCapturing || this.buffer.includes('<<<SUGGESTIONS:')) {
    const { suggestions } = extractSuggestionsFromText(this.buffer);
    this.buffer = '';
    return { textToEmit: '', suggestionsFound: suggestions.length > 0 ? suggestions : null };
  }
  const textToEmit = this.buffer;
  this.buffer = '';
  return { textToEmit, suggestionsFound: this.suggestions.length > 0 ? this.suggestions : null };
}
```

`this.suggestions` wird in `processChunk()` gesetzt, sobald der schließende `>>>`-Delimiter erkannt wird — an derselben Stelle, an der `processChunk()` bereits `suggestionsFound: suggestions` an den Aufrufer zurückgibt. `stream.ts` konsumiert `flush()` am Stream-Ende genauso wie jeden `processChunk()`-Aufruf: `if (suggestionsFound && suggestionsFound.length > 0) { controller.enqueue(...) }`. Da der zweite Zweig von `flush()` **unbedingt** `this.suggestions` zurückgibt, sobald es nicht leer ist — unabhängig davon, ob es bereits einmal über `processChunk()` gesendet wurde — sendete jede Guide-Antwort mit Vorschlägen (laut Prompt-Design praktisch jede Antwort) das identische `data: {"suggestions": [...]}\n\n`-Event zweimal an den Client.

Zwei bestehende Tests bestätigten dieses Verhalten fälschlich als korrekt: `chat-guide-suggestions.test.ts` Zeile 89-91 und `chat-guide-regression.test.ts` Zeile 205-207/210-217 assertierten jeweils, dass `flush()` nach einem bereits erfolgreichen `processChunk()`-Fund dasselbe Array erneut zurückgibt.

**Verifizierter Ist-Stand (2026-09-07, vor L2):** `route.ts`s Nicht-Streaming-Zweig (vor L2):

```ts
return apiSuccessResponse(
  { answer: answerResult.answer, contextVersion: CASINO_GUIDE_CONTEXT_VERSION },
  { headers: responseHeaders },
);
```

`answerResult` ist ein `GuideAnswerResult` (`types.ts`), das `suggestions?: string[]` deklariert und das `answer.ts` auf jedem seiner Return-Pfade bereits korrekt befüllt (`suggestions: suggestions.length > 0 ? suggestions : undefined`). Die obige Response-Konstruktion griff aber nur auf `answerResult.answer` und die statische `contextVersion` zu — `answerResult.suggestions` wurde nie gelesen. `useGuideChatStream.ts`s „Classic JSON fallback"-Zweig (greift, wenn `stream: false` angefragt wird oder die Response kein `text/event-stream` ist) prüft bereits `'suggestions' in payload && Array.isArray(payload.suggestions)` — der Client-Contract erwartete dieses Feld also längst, nur der Server lieferte es im Nicht-Streaming-Fall nie. Derselbe Root-Cause (ein bereits korrekt berechnetes `GuideAnswerResult`-Feld, das `route.ts`s Response-Objekt nicht erreicht) betraf parallel `action` — siehe [`07_ui_action_control.md`](07_ui_action_control.md) §3 L2-Abschnitt, wo dieser Fund zuerst identifiziert wurde.

## 4 — Meilensteine

### L1 — Doppel-Emission der Suggestions bei `flush()` beheben ✅ ausgeführt (2026-09-06)

- **Ziel:** Die in §2 #6/#7 benannte Lücke schließen — `flush()` darf ein bereits über `processChunk()` gesendetes Suggestions-Array nicht erneut zurückgeben, der legitime „unvollständiger Delimiter bis Stream-Ende"-Fallback bleibt aber unangetastet.
- **Umsetzung:** Neues privates Feld `suggestionsEmitted: boolean` (Default `false`) wird in beiden `processChunk()`-Zweigen, die Suggestions zurückgeben, zusammen mit `this.suggestions` gesetzt. `flush()` prüft `suggestionsEmitted` in beiden eigenen Zweigen zuerst und gibt `suggestionsFound: null` zurück, falls bereits gesendet — andernfalls setzt es `suggestionsEmitted = true` und sendet wie zuvor (deckt weiterhin den Fall ab, dass der Delimiter erst am Stream-Ende ohne vorherigen `processChunk()`-Treffer vollständig vorliegt).
- **Korrigierte/neue Tests:** `chat-guide-suggestions.test.ts` — die bestehende Assertion in „intercepts delimiter block arriving across chunk boundaries" korrigiert (`toBeNull()` statt Duplikat) und ein neuer dedizierter Test „never emits the same suggestions array twice for one response" ergänzt. `chat-guide-regression.test.ts` — zwei bestehende Assertions in „emits the leading text and captures suggestions..." und der umbenannten „does not re-emit already-captured suggestions on flush..." korrigiert.
- **Verifizierung (2026-09-06):** `npm run typecheck` 0 Fehler · `npm run test` 1633/1633 grün (215 Dateien) · `npm run lint` 0 Fehler (23 vorbestehende Warnungen, keine in den geänderten Dateien) · `npm run build` erfolgreich (nach Bereinigung eines veralteten `.next`-Cache-Artefakts, wie bereits in vorherigen Härtungen dieser Konversation dokumentiert) · `git status --short` zeigt nur `src/lib/casino/chat-guide/suggestions.ts` (M), `src/lib/casino/__tests__/chat-guide-suggestions.test.ts` (M) + `src/lib/casino/__tests__/chat-guide-regression.test.ts` (M).

### L2 — `suggestions` im Nicht-Streaming-Antwortpfad ausliefern ✅ ausgeführt (2026-09-07)

- **Ziel:** Die in §2 #11 / §3 (L2-Abschnitt) benannte Lücke schließen — ein vom Modell erzeugter Follow-up-Vorschlag muss den Client auch dann erreichen, wenn der Endpunkt ohne Streaming aufgerufen wird.
- **Umsetzung:** `route.ts`s Nicht-Streaming-Zweig gibt jetzt `{ answer: answerResult.answer, action: answerResult.action, suggestions: answerResult.suggestions, contextVersion }` zurück (das `action`-Feld kam bereits durch die zeitgleiche Kategorie-7-L2-Härtung hinzu, siehe [`07_ui_action_control.md`](07_ui_action_control.md) §4 L2). `answer.ts` selbst musste nicht geändert werden — es befüllte `suggestions` bereits korrekt.
- **Neuer Test:** `chat-guide-route.test.ts` — Regressionstest, der `requestCasinoGuideAnswer` mit einem `suggestions`-Array mockt und prüft, dass die vollständige JSON-Response dieses Array unverändert enthält.
- **Verifizierung (2026-09-07):** `npm run typecheck` 0 Fehler · `npm run test` 1663/1663 grün (217 Dateien, +1 neuer Test) · `npm run lint` 0 Fehler (30 Warnungen gesamt, keine in den 2 geänderten Dateien) · `npm run build` erfolgreich · `git status --short` zeigt nur `src/app/api/chat/bot-response/route.ts` (M) + `src/lib/security/__tests__/chat-guide-route.test.ts` (M) — `route.ts` trägt zu diesem Zeitpunkt bereits die zeitgleiche Kategorie-7-L2-Änderung (`action`-Feld) aus derselben Session.

## 5 — Definition of Done

1. `flush()` gibt niemals ein bereits über `processChunk()` zurückgegebenes Suggestions-Array ein zweites Mal zurück. _(L1)_
2. Der legitime Fallback (unvollständiger Delimiter bis Stream-Ende) funktioniert weiterhin unverändert. _(L1)_
3. Kein bestehender Test kodiert mehr das fehlerhafte Doppel-Emissions-Verhalten als Soll-Zustand. _(L1)_
4. Der Fix ist durch einen dedizierten, deterministischen Regressionstest zusätzlich zu den beiden korrigierten Bestandstests abgesichert. _(L1)_
5. `route.ts`s Nicht-Streaming-Zweig reicht `answerResult.suggestions` unverändert in die JSON-API-Response weiter. _(L2)_
6. Die Response-Form für Antworten ohne Suggestions bleibt unverändert (kein Regressions-Risiko an bestehenden Tests). _(L2)_

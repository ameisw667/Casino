## 3 — Verifizierter Ist-Stand (2026-09-06, vor L1; L2-Fund unten separat datiert)

`useGuideChatStream.ts` Zeilen 148–154 (vor L1):

```ts
const history = turns
  .filter((t) => t.id !== 'royale-guide-intro')
  .slice(-6)
  .map((t) => ({
    role: t.role === 'player' ? ('user' as const) : ('assistant' as const),
    content: t.text,
  }));
```

`t.text` wird unverändert übernommen — für einen `guide`-Turn ist das der vollständig akkumulierte Streaming-Text (`t.text + chunkText` in der SSE-Verarbeitungsschleife, keine Obergrenze während der Akkumulation). `bot-response/route.ts:26-40` (`guideHistoryItemSchema.content: z.string().trim().max(1000)`, Array `.max(6)`) validiert die eingehende `history` **als Ganzes** — Zod's `safeParse` gibt bei einem einzelnen zu langen Item `success: false` für das **gesamte** Array zurück, nicht nur für das betroffene Element. `sendQuestion()`s `!response.ok`-Zweig (Zeilen 175–194) behandelt nur `401` und `429` differenziert; jeder andere Fehlerstatus (inklusive `400`) führt zur generischen Nachricht „Royale Guide ist vorübergehend nicht erreichbar. Bitte versuche es gleich erneut." — der Spieler bekäme also nie einen Hinweis darauf, dass ein zu langer vorheriger Turn die Ursache war, und jede weitere Nachricht in derselben Konversation würde denselben Fehler wiederholen, solange der lange Turn innerhalb der letzten 6 Positionen bleibt.

`hooks.test.ts` deckte vor dieser Härtung nur ab, dass die drei Guide-Hooks als Funktionen exportiert werden — keine Testabdeckung für `sendQuestion()`s interne History-Konstruktion.

**Verifizierter Ist-Stand (2026-09-07, vor L2):** In `sendQuestion()` legen drei Stellen einen Turn mit `role: 'guide'` an, der **keine echte Modellantwort** enthält: (1) der `!response.ok`-Zweig (Zeilen ~187–206, generische/401/429-Hinweistexte), (2) der `!accumulated.trim()`-Zweig nach einem leeren SSE-Stream (Zeilen ~269–280, „Royale Guide konnte keine Antwort generieren…"), (3) der äußere `catch`-Block bei einer Netzwerk-Exception (Zeilen ~324–333). `GuideTurn` (`guide-config.ts`) hatte vor L2 kein Feld, das einen solchen Turn von einer echten Antwort unterschied — `role` ist bei beiden identisch `'guide'`. `buildGuideHistoryPayload()` (L1-Stand) filterte ausschließlich `t.id !== 'royale-guide-intro'`, keine dieser drei Fallback-Turns. Ergebnis: Stellt ein Spieler innerhalb der letzten 6 Turns eine weitere Frage, nachdem einer dieser drei Fälle aufgetreten ist, wird die generische Fehlernachricht als vermeintlich eigene, vorherige Antwort des Modells in `messages` (`stream.ts`) eingereiht und an OpenAI gesendet — eine Fabrikation, die das Modell nie erzeugt hat. `GuideMessageList.tsx` rendert diese Turns zudem optisch identisch zu echten Antworten (keine bestehende Fehler-Kennzeichnung im UI), was den Fund zusätzlich bestätigt: Es gibt im gesamten Codepfad keine Stelle, die zwischen „echter Modell-Turn" und „Client-Notiz" unterscheidet, bevor L2 dieses Flag einführt.

## 5 — Definition of Done

1. Kein einzelner History-Turn kann mehr die gesamte `history`-Zod-Validierung zum Scheitern bringen. _(L1)_
2. Die History-Konstruktionslogik ist als reine, unit-testbare Funktion isoliert, ohne eine neue Test-Abhängigkeit einzuführen. _(L1)_
3. Verhalten für kurze Turns (< 1.000 Zeichen) bleibt byteidentisch zum vorherigen Verhalten. _(L1)_
4. Der Fix ist durch 3 dedizierte, deterministische Unit-Tests regressionsgesichert. _(L1)_
5. Ein client-generierter Fallback-/Fehler-Turn wird nie Teil der an das Modell gesendeten `history`. _(L2)_
6. Echte Spieler- und Modell-Turns bleiben in Reihenfolge und Inhalt unverändert, wenn kein Fallback-Turn dazwischenliegt (keine Regression an #1–#4). _(L2)_
7. Die visuelle Darstellung im Chat-UI bleibt für alle Turn-Typen unverändert (reine Datenfluss-Korrektur). _(L2)_

## 3 — Verifizierter Ist-Stand (2026-09-06, vor dieser Härtung)

`stream.ts` Zeile 272–277 (vor L1):

```ts
} catch (err) {
  controller.enqueue(
    encoder.encode(
      `data: ${JSON.stringify({ error: err instanceof Error ? err.message : 'Stream Error' })}\n\n`,
    ),
  );
}
```

Dieser Block wird ausschließlich erreicht, wenn `reader.read()` (oder ein nachgelagerter Verarbeitungsschritt innerhalb der `while`-Schleife) nach mindestens einem erfolgreichen Chunk fehlschlägt — der Stream wurde also bereits geöffnet und kann nicht mehr auf den strukturierten `requestCasinoGuideAnswer()`-Fallback umschalten (im Unterschied zu den beiden Fallback-Pfaden vor Stream-Start, §2 #4). `err.message` landete unverändert im `error`-Feld des SSE-Events, ohne serverseitiges Logging. Alle anderen Guide-Fehlerpfade im Projekt (`bot-response/route.ts`, `chat/feedback/route.ts`, `admin/evals/route.ts`) geben stattdessen ausschließlich generische Client-Nachrichten zurück und loggen Details serverseitig via `CasinoLogger.error` — dieser eine Pfad war die Ausnahme.

`chat-guide-streaming.test.ts` deckte vor dieser Härtung 2 Fälle ab (Erfolgsfall, Upstream-Fehler **vor** Stream-Start); keiner davon erreichte den `catch`-Block innerhalb von `ReadableStream.start()`.

## 4 — Meilensteine

### L1 — Message-Leak im SSE-Fehler-Event schließen ✅ ausgeführt (2026-09-06)

- **Ziel:** Die in §2 #5/#6/#9 benannte Lücke schließen — ein Fehler nach Stream-Start darf keinen rohen internen Fehlertext mehr an den Client senden; stattdessen wird er serverseitig geloggt und der Client bekommt dieselbe generische Nachricht wie alle anderen Guide-Fehlerpfade.
- **Umsetzung:** `stream.ts` importiert `CasinoLogger` und ruft im `catch (err)`-Block `CasinoLogger.error('ChatGuideStream', 'SSE stream failed mid-response', err instanceof Error ? err : undefined)` auf, bevor `data: { error: 'Casino guide is temporarily unavailable' }` (identischer Wortlaut wie `CasinoGuideError`/`bot-response/route.ts`) in den Stream geschrieben wird.
- **Neuer Test:** `chat-guide-streaming.test.ts` — „never leaks the raw internal error message into the SSE error event once streaming has started" — simuliert einen OpenAI-Stream, der nach dem ersten Chunk in `pull()` wirft (`ECONNRESET talking to internal-postgres-host:5432`), liest den resultierenden Client-Stream vollständig aus und prüft, dass weder die Fehlermeldung noch der Hostname im ausgelieferten Payload vorkommen, wohl aber die generische Nachricht.
- **Verifizierung (2026-09-06):** `npm run typecheck` 0 Fehler · `npm run test` 1620/1620 grün (214 Dateien, +1 neuer Test) · `npm run lint` 0 Fehler (22 vorbestehende Warnungen, keine im geänderten File) · `npm run build` erfolgreich (nach Bereinigung eines veralteten `.next`-Cache-Artefakts, das mit dieser Änderung nichts zu tun hatte — Clean-Rebuild bestätigt) · `git status --short` zeigt nur `src/lib/casino/chat-guide/stream.ts` (M) + `src/lib/casino/__tests__/chat-guide-streaming.test.ts` (M).

### L2 — Telemetrie-Korrektur bei Mid-Stream-Fehlern ✅ ausgeführt (2026-09-07)

- **Ziel:** Die in §2 #10 benannte Lücke schließen — der echte OpenAI-Streaming-Pfad darf `outcome: 'success'` nicht mehr melden, bevor der Stream tatsächlich (erfolgreich oder mit Fehler) abgeschlossen ist. Ein Mid-Stream-Fehler muss eine telemetrisch sichtbare Spur hinterlassen statt lautlos hinter einer bereits gemeldeten `'success'`-Zeile zu verschwinden.
- **Umsetzung:**
  - `stream.ts`: `requestCasinoGuideAnswerStream()` erfasst jetzt `streamStartedAt = performance.now()` am Funktionseintritt. Im echten Streaming-Pfad (die dritte, OpenAI-`ReadableStream`-basierte Variante) wird `recordGuideTelemetry({ outcome: 'success', ... })` erst **nach** dem `[DONE]`-Chunk aufgerufen (also nach tatsächlichem, vollständigem Abschluss) statt vom Aufrufer vor Streaming-Beginn. Der bestehende `catch (err)`-Block (L1) ruft zusätzlich `recordGuideTelemetry({ outcome: 'upstream', ... })` auf, bevor er die generische Fehlermeldung in den Stream schreibt.
  - `types.ts`: `GuideStreamResult` bekommt ein neues Feld `telemetryHandledInStream: boolean` — `true` für den echten Streaming-Pfad (Telemetrie wird jetzt intern in `stream.ts` gemeldet), `false` für die beiden Vor-Stream-Fallback-Pfade (unverändertes Verhalten: `route.ts` meldet weiterhin sofort, da die Antwort dort schon vollständig vorliegt und kein Mid-Stream-Risiko besteht).
  - `route.ts`: Der bisher unbedingte `recordGuideTelemetry({ outcome: 'success', ... })`-Aufruf direkt nach `requestCasinoGuideAnswerStream()` wird jetzt nur noch ausgeführt, wenn `!streamResult.telemetryHandledInStream` gilt — verhindert eine doppelte (und im Fehlerfall falsche) Erfolgsmeldung für den echten Streaming-Pfad.
- **Test-Anpassungen (`chat-guide-streaming.test.ts`):** `recordGuideTelemetry` wird jetzt via `vi.mock('@/lib/casino/guide-telemetry', importOriginal)` partiell gemockt (nur diese eine Funktion, damit `normalizeGuideUsage` & Co. für den nicht betroffenen `requestCasinoGuideAnswer()`-Fallback-Pfad unverändert real bleiben). Drei bestehende Tests bekommen zusätzliche Assertions: der Erfolgstest prüft `telemetryHandledInStream === true` + `recordGuideTelemetry` mit `outcome: 'success'` nach vollständigem Stream-Read; der Vor-Stream-Fallback-Test prüft `telemetryHandledInStream === false` + dass `recordGuideTelemetry` **nicht** aus `stream.ts` aufgerufen wird; der bereits bestehende Mid-Stream-Fehlertest (L1) bekommt jetzt eine echte `userId` und prüft zusätzlich, dass `recordGuideTelemetry` genau einmal mit `outcome: 'upstream'` aufgerufen wird und **nie** mit `outcome: 'success'`.
- **Verifizierung (2026-09-07):** `npm run typecheck` 0 Fehler · `npm run test` 1657/1657 grün (216 Dateien) · `npm run lint` 0 Fehler (23 vorbestehende Warnungen, keine in den 4 geänderten Dateien) · `npm run build` erfolgreich · `git status --short` zeigt nur `src/app/api/chat/bot-response/route.ts` (M), `src/lib/casino/chat-guide/stream.ts` (M), `src/lib/casino/chat-guide/types.ts` (M), `src/lib/casino/__tests__/chat-guide-streaming.test.ts` (M).

## 5 — Definition of Done

1. Ein Fehler, der nach dem ersten erfolgreich gestreamten Chunk auftritt, sendet niemals mehr `err.message` an den Client. _(L1)_
2. Derselbe Fehler hinterlässt eine serverseitige Log-Zeile mit ausreichend Kontext für Debugging. _(L1)_
3. Der Erfolgspfad und der Vor-Stream-Fallback-Pfad bleiben unverändert (keine Regressionen in den bestehenden Tests). _(L1, weiterhin gültig nach L2)_
4. Der Fix ist durch einen dedizierten, deterministischen Mid-Stream-Fehlertest regressionsgesichert (kein Live-OpenAI-Aufruf nötig). _(L1)_
5. `recordGuideTelemetry` meldet für den echten Streaming-Pfad `outcome: 'success'` erst nach tatsächlichem Stream-Abschluss, nie beim bloßen Öffnen des Streams. _(L2)_
6. Ein Mid-Stream-Fehler hinterlässt eine Telemetriezeile mit einem Nicht-Erfolgs-`outcome` — nie ausschließlich eine bereits gemeldete `'success'`-Zeile. _(L2)_
7. Die beiden Vor-Stream-Fallback-Pfade melden weiterhin sofort und unverändert (keine Regression an einem bereits korrekten Pfad). _(L2)_

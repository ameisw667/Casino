## 3 — Verifizierter Ist-Stand (2026-09-06, vor dieser Härtung)

`useGuideAttachment.ts` Zeilen 11–22 (vor L1):

```ts
const handleFileSelect = useCallback(async (file: File) => {
  if (!isAllowedImageFile(file)) return;
  try {
    setIsCompressing(true);
    const compressed = await compressImageFile(file);
    setAttachedImage(compressed);
  } catch {
    // Ignore invalid files silently
  } finally {
    setIsCompressing(false);
  }
}, []);
```

`compressImageFile()` (`image-compression.ts`) kann aus mehreren Gründen scheitern: Canvas-2D-Kontext nicht initialisierbar, Bild kann nicht geladen werden (`img.onerror`), oder das komprimierte Ergebnis überschreitet trotz Skalierung `MAX_COMPRESSED_IMAGE_BYTES` (2,5 MB). Jeder dieser Fälle landete im selben leeren `catch`-Block — kein `CasinoLogger`-Aufruf (im Unterschied zum strukturell identischen `useGuideVoiceRecorder.ts`, das bei einem Mikrofon-Fehler sowohl loggt als auch eine `voiceStatusMessage` für den Spieler setzt), kein State-Signal für die aufrufende Komponente. Da das Bild den Browser bei einem Kompressionsfehler nie verlässt, gab es auch keine serverseitige Spur (kein Request, kein Log).

`image-compression.test.ts` deckte vor dieser Härtung nur `isAllowedImageFile`, `calculateScaledDimensions` und die `MAX_COMPRESSED_IMAGE_BYTES`-Konstante ab — die eigentliche `compressImageFile()`-Funktion (und damit der komplette Fehlerpfad) hatte keine Testabdeckung.

## 4 — Meilensteine

### L1 — Stillen Catch-Block bei fehlgeschlagener Bildkompression schließen ✅ ausgeführt (2026-09-06)

- **Ziel:** Die in §2 #7/#8/#10 benannte Lücke schließen — ein fehlgeschlagener Kompressionsversuch wird jetzt geloggt und als unterscheidbarer Fehlerzustand exponiert, statt komplett unbeobachtbar zu bleiben.
- **Umsetzung:** Neue exportierte Funktion `processGuideAttachment(file)` in `image-compression.ts` kapselt `isAllowedImageFile` + `compressImageFile` hinter einem diskriminierten Rückgabewert (`{ status: 'accepted', dataUrl }` / `{ status: 'rejected', reason: 'invalid-type' }` / `{ status: 'rejected', reason: 'compression-failed', error }`). `useGuideAttachment.ts`s `handleFileSelect` ruft diese Funktion auf, setzt bei `compression-failed` einen `CasinoLogger.error('useGuideAttachment', 'Image compression failed', ...)`-Aufruf ab (analog zum bestehenden Muster in `useGuideVoiceRecorder.ts`) und exponiert eine neue `attachmentError: string | null` aus dem Hook (aktuell noch ungerendert, siehe §2 #9 für den bewusst offen gelassenen UI-Anschluss).
- **Neue Tests:** `image-compression.test.ts` — „rejects an unsupported file type without attempting compression" und „reports a compression failure as its own distinct, inspectable outcome instead of silently discarding it". Der zweite Test nutzt bewusst **kein** Mocking: Vitests Node-Testumgebung hat kein `window`/`document`, wodurch die echte `compressImageFile()`-Implementierung natürlich in ihren bereits bestehenden „Canvas compression is only available in the browser"-Fehlerpfad läuft — ein realistischer statt simulierter Fehlerfall.
- **Verifizierung (2026-09-06):** `npm run typecheck` 0 Fehler · `npm run test` 1632/1632 grün (215 Dateien, +2 neue Tests) · `npm run lint` 0 Fehler (23 vorbestehende Warnungen, keine in den geänderten Dateien) · `npm run build` erfolgreich (nach Bereinigung eines veralteten `.next`-Cache-Artefakts, wie bereits in vorherigen Härtungen dieser Konversation dokumentiert) · `git status --short` zeigt nur `src/lib/casino/image-compression.ts` (M), `src/components/social/casino-guide/hooks/useGuideAttachment.ts` (M) + `src/lib/casino/__tests__/image-compression.test.ts` (M).

1. Ein fehlgeschlagener Kompressionsversuch hinterlässt eine serverseitig sichtbare Log-Zeile (Sentry via `CasinoLogger.error`).

3. Der Erfolgspfad (gültiges Bild, erfolgreiche Kompression) bleibt byteidentisch zum vorherigen Verhalten.

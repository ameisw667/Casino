## 2 — Self-Contained Kontext-Koffer

### (a) Trigger-Regel — „Wann entsteht ein Memory-Kandidat?" (primärer Ablageort: dieser Plan)

> Ein Memory-Kandidat (beliebigen Typs: `project`, `feedback`, `user`, `reference`) entsteht genau dann, wenn eine Session mit **einem** der vier Muster endet oder darin gipfelt: (1) eine **lernreiche Commit-Welle** — ≥ 5 thematisch zusammenhängende Commits mit Architektur-, Infrastruktur- oder Verfahrens-Ergebnis (Beispiele: DB-Pooling-Chaos-Hardening 2026-09-13, K0–K8-Execution-Welle 2026-09-14); (2) eine abgeschlossene **Options-Gate-Entscheidung** nach `xx_sop/01_workflow_jan_option_gate.md`, deren gewählte Option künftige Sessions bindet; (3) eine **Security-/DB-Härtungsrunde** (z. B. Chaos-Hardening, Migrations-Rolle, CSP-/CSRF-Änderung); (4) ein **wiederholter Fehler**, der ≥ 2× in getrennten Sessions identisch auftrat (Pfad: `learn-eval` statt Planungsdatei-Prosa, gemäß `CLAUDE.md` „Session-Kontinuität"). Konsequenz in allen vier Fällen: Das LLM formuliert **einen** Entwurf (Fakt / Warum lerntauglich / How to apply, plus Frontmatter mit Typ) und legt ihn Jan als **Schreibvorschlag** vor — **nie Auto-Write** (globale Regel „Write to memory **only when I explicitly ask**"). Jan-Freigabe = Gate G1; erst danach Datei anlegen und Index-Zeile in `MEMORY.md` ergänzen. Trifft keines der Muster zu, entsteht kein Kandidat — auf Nachfrage genügt eine 1-sätzige Skip-Entscheidung.

**Ablage-Regel:** Dieser Absatz ist die **primäre** Ablage. [`../01_6_memory_files.md`](../01_6_memory_files.md) Position 7 bekommt nur eine Verweiszeile auf diesen Plan (Ziel L0); [`06_u03_typ_abdeckung_project_plan.md`](06_u03_typ_abdeckung_project_plan.md) §2c reduziert sich auf dieselbe Verweiszeile — die dortige project-spezifische Ausformulierung („≥ 5 thematisch zusammenhängende Commits") ist hier in Trigger (1) vollständig übernommen, es geht kein Inhalt verloren. Die project-Instanziierung der Regel (welche Kandidaten aus Trigger (1) tatsächlich als project-Typ landen) bleibt in 06_u03 §2c-Kontext verlinkt, nicht kopiert.

### (b) Latenz-Regel — „Regeländerung und Memory-Update im selben Arbeitsschritt"

> Wird eine Verhaltens- oder Präferenzregel geändert (`t_claude_code/**`, `CLAUDE.md`, SOP), die durch einen bestehenden Memory-Eintrag gespiegelt wird, schlägt das LLM den zugehörigen Memory-Update **im selben Arbeitsschritt** vor (Gate G1 wie oben) — nicht „bei Gelegenheit in einer späteren Session".

**Warum (belegter Fall):** `no-visual-check-frontend.md` — die überholende Regeländerung ist im Datei-Body selbst datiert (**„Update 2026-09-05"**, Jans wiederholte visuell-Prüf-Aufforderungen), aber die Datei wurde erst **2026-09-13 21:02** tatsächlich überschrieben: **8 Tage Latenz**, in denen jede neue Sitzung die überholte „nie visuell prüfen"-Regel unverändert geladen hat (Bewertungs-Basis §Detailanmerkung 5). Gegenprobe: `verify-paths-before-recommending.md` — Anlass und Write fielen in dieselbe Sitzung (09-13 20:51), Latenz ≈ 0 Tage. Beide Fälle stammen aus demselben Audit-Fenster; die Kopplung ist also machbar, sie war nur nicht Regel. Jede Woche Latenz-Verzug ist eine Woche, in der Sessions gegen die falsche Regel arbeiten — deshalb ist die Latenz als eigenständige Regel gewichtet (Subsub 5, 14 %).

### (c) Kadenz-Ziel — prüfstichwort-artig formuliert

Ziel ist **nicht** „X Einträge/Woche" (das würde die burstförmige Struktur belohnen, solange die X irgendwann im Batch erreicht werden). Ziel ist ereignisgekoppelt:

> **Prüfstichwort (je Session / je Plan-Abschluss abfragbar):** „Für jedes identifizierte lernreiche Ereignis existiert genau einer von zwei Belegen: (i) **1 Memory-Schreibvorgang** (via Gate G1) oder (ii) **1 dokumentierte Skip-Entscheidung** (1 Satz mit Grund, abgelegt im Ausführungs-Log des zuständigen Plans in `Planungsdateien/` bzw. als Zeile im Session-Report). Kein dritter Zustand."

**Ablageort der Skip-Entscheidung (präzisiert 2026-09-17):** `worldmap/00_WORLDMAP_STATUS.md` ist als Ablage **gestrichen** — der dafür nötige Abschnitt „Aktive Pläne" existiert dort nicht (verifiziert; dieselbe Abweichung wie in 06_u03/06_u04/06_u05/06_u06/06_u09/06_u10). Damit die Skip-Spur trotzdem dauerhaft und auffindbar bleibt, gilt: Skip-Entscheidungen werden in der **zuständigen Plan-Datei** (Ausführungs-Log) oder bei planlosen Ereignissen in `01_5_session_memory.md` §3 notiert — nie nur im Chatverlauf.

Damit wird die eigentliche Bottleneck-Metrik (Subsub 2: Kadenz vs. Projektaktivität) messbar, ohne die absolute Frequenz (Subsub 1) künstlich zum Ziel zu machen: Eine ruhige Woche mit 0 Commits erfordert 0 Schreibvorgänge; eine Commit-Welle wie 09-05→09-13 (83 Commits, darunter DB-Pooling-Hardening und Query-Perf-Gate) erfordert mindestens je Ereignis Schreibvorgang **oder** begründete Skip-Entscheidung.

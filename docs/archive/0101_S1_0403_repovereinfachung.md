## 5 — Phase 1: Sweep, nur Report

### L1 — Scanner-Läufe (billig, mechanisch, zuerst)

- Ausführung: `npx -y knip`, `npx -y depcheck`, `npx -y ts-prune` — **ohne** `package.json`- oder Config-Änderung im Repo; ts-prune ohne Flag starten (kein `--version` vorhanden).
- **4. Scanner `madge`** (`npx madge --circular --extensions ts,tsx src`) — bereits als devDep im Repo (verifiziert 2026-08-30), liefert die Fundklasse **zyklische Importe/orphanartige Abhängigkeitsinseln**, die die anderen drei Scanner nicht abdecken und beim manuellen Querlesen systematisch untergehen.
- **Rohprotokoll:** Jeder Scanner-Lauf wird als Vollausgabe in `T_FRONTEND/0101_S1_0403_repovereinfachung_scanner-raw.md` (je Scanner ein Abschnitt + Befehlszeile + Messdatum) gesichert; die Fundmatrix dokumentiert nur die danach klassifizierten Funde.
- **Klassifikationsschritt (Pflicht nach jedem Lauf):** jede Meldung wird eingestuft als `Hinweis (prüft L2/L3)` · `False Positive (benannt)` · `Fund (mit Zeilenbeleg)`. Unklassifizierte Scanner-Meldungen ergeben am Ende automatisch ein Fund (Kategorie NOTE: „ungeprüft") — damit entsteht kein stillschweigender Schwebezustand.
- Ausnahme-Konventionen für den Scanner dokumentieren (bekannte False-Positive-Quellen):
  - **Dynamische Imports** (`await import(...)`), Trigger.dev-Tasks, Middleware (`src/proxy.ts`), Root-Konfig-Dateien (`next.config.ts`, `playwright.config.ts`) — Exporte werden von Tools oft als „ungesucht" gemeldet.
  - **Next.js-Konventionen**: `page.tsx`, `layout.tsx`, `loading.tsx`, `error.tsx`, `route.ts` sind Entry-Points ohne importierende Datei — niemals allein als „tot" melden.
  - **Test-Mocks/Vi-mocks**: in `__tests__` referenzierter Code ist nicht tot, selbst wenn keine Produkt-Importkette ihn erreicht.
- **Verifizierungsregel (hart):** „tot" wird erst behauptet, wenn der Kontext gelesen wurde — ein Export gilt erst nach durchschnittlicher Prüfung aller Importstellen (Grep + Eigenlese) als tot. Scanner-Ergebnisse sind Hinweise, keine Befunde.

### L2/L3 — Querlesen (teuer, die eigentliche Usage-Masse)

- **Ausführungsbatching (Kontextgrenze):** Eine LLM-Session kann 500+ Dateien nicht seriös im Kontext halten. Das Querlesen läuft deshalb in **Batches von 10–20 Dateien pro Lesedurchgang** (subagentenbasiert, Fundliste je Batch zurückgeben), nicht als ein monolithischer Leselauf. Die Batch-Grenze ist der harte Abbruchpunkt je Durchgang — verhindert, dass ab Minute 30 beleglose Behauptungen entstehen.
- Welle 1 (L2): `src/lib/**` — 254 Dateien. Fokus: 39 Root-Module von `src/lib/casino/`, `lib/security/**` (nur Kategorien „toter Code"/„Duplikate"), `lib/analytics/**` (strikte Zod-Allowlist — Berührungen nur melden).
- Welle 2 (L3): `src/components/**` + `src/app/**` — 506 Dateien. Eigener Checkblock: `src/app/testing/**` (94) — Sandbox-Bedarf dokumentieren statt still löschen.
- Pro Datei nur die 6 Fundkategorien abprüfen: **toter Code · Duplikate · ungenutzte Dependencies · tote/veraltete Tests · unnötige Komplexität (YAGNI) · Musterverstöße/Wiederholung.**
- **Fester Timebox-Auftrag je Welle:** „Fertig, wenn `src/lib/**` (L2) bzw. `components+app` (L3) vollständig gemappt ist ODER die Timebox endet." Bei Abbruch: Fundmatrix-Abschnitt **„Bearbeitungsstand"** pflegen (`bearbeitet bis Datei X / verbleibend: Dateien Y–Z`) — kein Schein-Abschluss.
- Meldedosierungs-Regel: Funde ohne echten Beitrag (Stil-Nüancen, Einzeiler-Duplikate, was ESLint ohnehin fängt) bewusst NICHT melden — Over-Reporting verdirbt die Fundmatrix.

### L4 — Fundmatrix-Format (Vorlage: `17_TO10_animations_fundmatrix.md`)

Pfad: `docs/archive/17_TO03_simplify_fundmatrix.md`. Kopf: Stand/Typ/Plan-Verweis/„lokal verifiziert (Eigenlese + Grep mit Zeilenbeleg)". Je Fund:

| Spalte         | Inhalt                                                                                                                                                                                                                                                                                                                                                           |
| :------------- | :--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Beleg          | `Datei:Zeile` (Eigenlese verifiziert, Messdatum)                                                                                                                                                                                                                                                                                                                 |
| Kategorie      | eine der 6 oben (plus „Dependency")                                                                                                                                                                                                                                                                                                                              |
| Schwere        | CRITICAL / HIGH / MEDIUM / LOW / NOTE — **Definitionen:** CRITICAL = bewiesener toter/doppelter Code auf einem Weg, der Sicherheit oder Geld berührt (z. B. ungenutzter Wallet-Pfad) · HIGH = toter Code / Duplikat mit realem Wartungsschaden · MEDIUM = Urteils-Fix mit erkennbarem Nutzen · LOW = Kosmetik mit Beleg · NOTE = Beobachtung ohne Handlungsdruck |

**Zählkonvention:** 1 FUND = 1 Belegstelle (`Datei:Zeile`), nicht 1 Fund pro Datei bei mehreren Stellen — eine Datei mit 3 toten Exporten ergibt 3 Funde (verhindert Fusions-Unklarheit bei der Abstimmung).
**Secrets-Regel:** In der Fundmatrix werden **keine** Secrets, Env-Werte, DSNs oder Auth-Token-Zeilen zitiert — Funde aus `lib/security/**` werden auf Struktur/Existenz referenziert, nicht auf Inhalte.

## 6 — Phase 2: Fix-Welle (separat, bewusst NICHT Bestandteil des Sweeps)

- **Kein batchweises Fixen.** Jeder Fix ist ein eigener Auftrag mit eigenem Freigabe-Punkt (Jan entscheidet je Fund oder je Paket thematisch gleicher Funde).
- **Gates in fester Reihenfolge nach jedem Fix:** `npm run typecheck` → `npm run lint` → `npm run test` → `npm run build`. Ein Fix gilt erst nach grünen Gates als umgesetzt (SOP 02 §4: nur aktuelle Befehlsausgaben als Nachweis).
- **Gate-Blindstelle E4 (bekannt, mit Kompensation):** `npm run test` erfasst den `.tsx`-Test nicht (vitest-`include`-Bug, Eingangsfund E4) — die Tests sind bis zu dessen Fix systematisch lückenhaft. Kompen­sation: bei Fixes, deren einziger Absicherungstest eine `.tsx`-Datei wäre, werden typecheck + build als harte Gates doppelt gewichtet und der Fix bekommt die Notiz „Testabdeckung bis E4-Fix lückenhaft" in der Fundmatrix.
- **Residue-Check:** Bei Löschung ganzer Komponenten/Module ≥ 3 Dateien oder einer Route: vor Entfernung den Subagenten `casino-residue-scout` (report-only) nachschalten — Fundliste prüfen, Reste in `xx_docs`/`docs/**`/`T_FRONTEND/**` berücksichtigen.
- **Lösch-Regel für Sandboxes (`src/app/testing/**`):** Bedarf erst mit Jan klären; Sandboxes sind explizit als bare Sandboxes in `layout.tsx`-Konvention verankert (siehe `xx_docs/09_layout_shell_context.md`) — still löschen wäre Doku-Drift.
- **Freigabepunkte bei Jan (Ausnahme-Liste, im Übrigen vollständig LLM):**
  1. Start von Phase 2 (Sammel-Freigabe „ab hier darfst du fixen").
  2. Jeder Klasse-3-Fund (Sonderfälle inkl. Wallet-/Auth-/Settlement-Dateien).
  3. Jede Dependency-Entfernung in `package.json` (E1/E2).
  4. Commit-Wort (global: Commits nur auf Jans Wort).
- **Sichtbare Verhaltenstest-Pflicht:** Fixes an Komponenten mit UI-Auswirkung bekommen eine visuelle Prüfung durch Jan (nicht durch das LLM), bevor sie als „grün" gelten.

## 4 — Top 3 im Detail

### Option A — Inline-Karte auf Design-Tokens heben

- **Was ändert sich:** `style={{...}}`-Objekte in `AuthForm.tsx` werden durch Tailwind-Klassen + zentrale Design-Tokens ersetzt (Farben, Spacing, Radius aus `globals.css`/Token-Datei statt Hex/HSL-Literalen). Struktur (eine zentrierte Karte, 420px) bleibt identisch.
- **Vorteil:** kleinster Diff, geringstes Risiko, sofort umsetzbar auch ohne Wartezeit auf `02_FRONTEND_REDESIGN.md`-Kohorte 1 (kann sie sogar vorwegnehmen als Testfall).
- **Nachteil:** löst das eigentliche „ungestylt wirkt generisch"-Problem nur oberflächlich — Layout bleibt ein Standard-Auth-Formular ohne Markenerlebnis. Ordnet sich am wenigsten unter „Anti-Template-Policy" aus den globalen Web-Regeln ein (Gefahr: bleibt ein „Default-Formular mit Farbwechsel").
- **Aufwand-Treiber:** 1 Datei (`AuthForm.tsx`), keine neuen Assets, keine neuen Dependencies.

### Option B — Split-Screen Members-Card (Empfehlung)

- **Was ändert sich:** Formular bleibt links (bestehende Feldlogik unverändert), rechte Bildschirmhälfte erhält ein Brand-Panel — z. B. Value-Props („Provably Fair", „Sofort-Auszahlung", VIP-Teaser), Gold-Akzent-Gradient, ggf. animiertes Emblem. Nutzt `Magnetic.tsx` für den Submit-Button und `VibeMotion.tsx` für Card-Entrance/Field-Focus statt der aktuellen manuellen `useState`-Hover-Logik.
- **Vorteil:** trifft direkt die im Code bereits als Zielrichtung festgehaltene „Members-Card"-Formulierung (`docs/architecture/02_CLERK_SUPABASE.md`). Erfüllt mehrere Punkte der Anti-Template-Checkliste (Hierarchie durch Zweispaltigkeit, Depth durch Glas-Layering, designte Hover/Focus-States) ohne neue Video-/Partikel-Infrastruktur. Mobile-Fallback einfach: rechte Spalte klappt weg, linke Spalte wird zur bekannten Ein-Karten-Ansicht (kein separates Mobile-Design nötig).
- **Nachteil:** mittlerer Aufwand — neues Layout-Grid, neue Copy für die rechte Spalte (Value-Props-Text), Motion-Wiring auf bestehende Primitives.
- **Aufwand-Treiber:** `AuthForm.tsx` (Struktur-Umbau), ggf. neue kleine Sub-Komponente `AuthBrandPanel.tsx`, keine neue DB/API-Berührung.
- **Risiko:** Niedrig — rein additive Layout-Änderung, Auth-Logik unangetastet, kein neuer Money-/Security-Pfad (bestätigt Roadmap-Einstufung „Security-Reviewer: Nein").

### Option C — Full-Bleed Cinematic (Liquid-Gold)

- **Was ändert sich:** Formular wird zur schwebenden Glas-Karte über einem vollflächigen, animierten Hintergrund (CSS-Gradient-Mesh oder leichtgewichtiger Canvas/SVG-Fluid-Effekt in Gold-Tönen statt Video).
- **Vorteil:** höchste visuelle Wirkung, trifft die zweite im Code notierte Zielrichtung („Liquid-Gold"). Stärkstes Wiedererkennungsmerkmal für einen ersten Eindruck.
- **Nachteil:** höchster Aufwand der Top 3 — Animation muss Performance-Budget einhalten (kollidiert potenziell mit noch offener Initiative 1.1 Mobile-LCP, da Auth-Seiten dann ebenfalls animierte Hintergründe tragen). Motion-Overload-Risiko: der bestehende Ambient-Glow-Effekt in `AuthForm.tsx` (radialer Gradient) ist bereits eine Mini-Version davon — C skaliert dieses Prinzip auf, braucht aber sorgfältige `prefers-reduced-motion`-Behandlung.
- **Aufwand-Treiber:** neue Animations-Logik (CSS `@keyframes` oder leichte Canvas-Lösung — keine schwere Lib, um Bundle-Budget aus `performance.md` nicht zu sprengen), `AuthForm.tsx`-Umbau, Reduced-Motion-Fallback.
- **Risiko:** Niedrig für Auth-Logik (unangetastet), aber Performance-Risiko höher als A/B — deshalb Rang 3 trotz stärkstem visuellen Ergebnis.

## 5 — Empfehlung

**Option B (Split-Screen Members-Card).** Begründung:

1. Trifft die bereits im Code hinterlegte Zielrichtung, ohne die zweite (Liquid-Gold-Animations-Komplexität) sofort mitzunehmen.
2. Bester Kompromiss aus Aufwand (Roadmap-Einstufung 22/100 bleibt realistisch — kein neues Motion-Framework, nur bestehende Primitives verdrahten) und Wirkung (erfüllt mehr Anti-Template-Kriterien als A).
3. Kollidiert nicht mit der noch offenen Mobile-Perf-Initiative 1.1 (kein schweres Animations-Payload).
4. Liquid-Gold-Motiv (Option C) lässt sich später **additiv** als Hintergrund-Layer in die B-Struktur nachrüsten, falls gewünscht — B blockiert C nicht, C würde B aber komplizierter machen, wenn zuerst umgesetzt.

**Falls Jan stattdessen den minimal-invasiven Weg will:** Option A ist die risikoärmste Wahl, sollte aber nicht als Endzustand missverstanden werden — würde die Anti-Template-Policy nur teilweise erfüllen.

## 9 — Architektur-Grundlage (Recherche vor Planung)

Vor der Aufwandsschätzung wurde der bestehende Code geprüft statt blind neu zu bauen (Prinzip DRY/YAGNI aus `coding-style.md`):

1. **`src/components/home/LobbyAmbientBackground.tsx` existiert bereits** und implementiert exakt das „Liquid-Gold"-Konzept: Canvas-Gold-Dust-Partikel + maus-folgender „Liquid Glasswater"-Spotlight-Gradient + Noise-Textur-Overlay. Bereits produktiv auf der Homepage (`HomeClientV2.tsx:37`). Bereits gehärtet: deaktiviert sich komplett unter 1024px (`window.matchMedia('(max-width: 1023px)')`, keine rAF-Loop, keine Listener auf Mobile) und reduziert Partikelzahl/-bewegung unter `prefers-reduced-motion`. → **Wiederverwenden statt neu bauen.**
2. **`.parallax-orb-gold` / `.parallax-orb-dark` / `orb-float-slow`** sind bereits in `globals.css` definiert (Zeilen ~1057–1101) — gleiche visuelle Idee (langsame, verschwommene Gold-/Dunkel-Orbs). Aber: **0 Verwendungen** im gesamten `src/`-Baum (grep bestätigt, tot) **und kein `prefers-reduced-motion`-Guard** (anders als das analoge `.v2-wheel-*`-Pattern in `styles/v2.css:710`, das einen Guard hat — Inkonsistenz/Bug). → Konzept wiederverwenden (Technik: `transform`-animierte, geblurrte Kreise = compositor-friendly gemäß `performance.md`), aber **eigene `auth-orb-*`-Klassen** anlegen statt die toten `.parallax-orb-*` zu kapern (vermeidet Kopplung, falls die Homepage sie später doch nutzt) + Guard beim Erstellen gleich mitliefern.
3. **`/sign-in` und `/sign-up` rendern innerhalb von `MainLayout`** (Header/Nav bleibt sichtbar — `ClientShell.tsx` hat für diese Routen keinen Sonderfall wie für `/admin` oder `/v2`). 4. **Tailwind ist in diesem Projekt nicht installiert** (kein `tailwindcss`-Package, keine `tailwind.config`, `prettier-plugin-tailwindcss` ist nur ein Class-Sortierer für den — hier ungenutzten — Fall). ## 11 — Kohorten & Reihenfolge

Reihenfolge nach aufsteigendem Risiko — Infrastruktur zuerst (kein Verhaltensrisiko), die Datei mit der größten Blast-Radius (`AuthForm.tsx`, gemeinsame Logik für 2 Routen) zuletzt vor der Verifikation:

### Kohorte 1 — CSS-Infrastruktur (`globals.css`)

- Neue Klassen `.auth-orb-gold`, `.auth-orb-dark` (analog `.parallax-orb-*`, eigener Namespace, nutzen die bestehende Keyframe `orb-float-slow` weiter — kein neues Keyframe nötig).
- Neue Klasse `.auth-cinematic-mobile-fallback` — statischer radialer Gold-Gradient ohne Animation, für `<1024px`.
- Neuer Block: `@media (prefers-reduced-motion: reduce) { .auth-orb-gold, .auth-orb-dark { animation: none !important; } }`.
- Risiko: quasi 0 (rein additiv, keine bestehende Klasse verändert).

### Kohorte 2 — `AuthCinematicBackground.tsx` (isoliert)

- `'use client'`, keine Props.
- Äußerer Wrapper: `position: absolute; inset: 0; pointerEvents: none; zIndex: 0; aria-hidden="true"` (identisches Sicherheitsmuster wie `LobbyAmbientBackground`, verhindert Klick-/Tab-Diebstahl vor dem Formular).
- Enthält: `<LobbyAmbientBackground />` (übernimmt eigenes Mobile-/Reduced-Motion-Gate) + 2 Orb-`div`s (nur ab 1024px sichtbar, per CSS `@media`, synchron zur internen Schwelle von `LobbyAmbientBackground`) + 1 Fallback-`div` (nur unter 1024px sichtbar).
- Kann isoliert im Dev-Server unter `/sign-in` geprüft werden, bevor Kohorte 3 das Formular selbst anfasst.

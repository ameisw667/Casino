### Audit-Trail: nach Erstellung gefundene und behobene Schwächen

1. **Erster Entwurf hätte `animation-fill-mode` nicht erwähnt** — CSS-Keyframe-Animationen ohne `forwards` können nach Abschluss auf den Ausgangszustand des letzten Keyframes zurückfallen oder bei Wiederholung Probleme machen. Korrigiert: M2.5 vergleicht explizit gegen die **M1-Messung derselben Session/Umgebung**, nicht gegen die Baseline vom 2026-07-28.
3. **Timing-Wahl (0,4s ease-out) war zunächst unbegründet** — ergänzt: Herleitung aus Framer-Motions Default-Tween-Dauer, mit explizitem Hinweis, dass die exakte Kurve nicht 1:1 übertragbar ist und Jans visuelle Freigabe das letzte Wort hat (keine Behauptung von Pixel-Perfektion ohne visuellen Check).

### Root-Cause-Nachforschung (ausgelöst durch das Nullergebnis — Plan sah genau das als Fehlerfall vor, siehe Abschnitt 5)

Statt direkt auf Fallback-Option A zu wechseln, wurde zuerst untersucht, **warum** Option B keine Wirkung zeigte — sonst hätte auch Option A wahrscheinlich ergebnislos geendet, ohne dass die eigentliche Ursache je gefunden worden wäre:

1. **`curl` gegen die rohe SSR-HTML-Antwort** (ohne JS-Ausführung) zeigt: **kein** `<main>`-Tag, **kein** „VIP CASINO."-Text im initial ausgelieferten HTML. Stattdessen: `<div>...INITIALIZING CASINO...</div>` als einziger sichtbarer Body-Inhalt (13 KB, fast nur `<head>`-Metadaten + Script-Tags).
2. **Quelle gefunden:** `src/components/layout/MainLayout.tsx:402-420` — `if (!mounted || !hasHydrated) { return <div>...INITIALIZING CASINO...</div>; }`. `MainLayout` umschließt **jede** Nicht-Admin-Route (laut `CLAUDE.md`-Architektur-Abschnitt „Layout Shell") und rendert bei fehlendem Mount/Hydration-Flag einen kompletten Platzhalter **statt** der eigentlichen Kinder — die echte Seite (inkl. `HomeClientV2`/LCP-Element) wird erst angehängt, wenn dieses Gate fällt.
3. **`hasHydrated`-Mechanik geprüft** (`src/store/useCasinoStore.ts:923-926`, `onRehydrateStorage`): wird synchron nach Zustand-`persist`-Rehydrierung (LocalStorage-Read) gesetzt — **kein Netzwerk-Roundtrip**, sollte also schnell sein. Der eigentliche Flaschenhals ist somit nicht „warten auf Server-Antwort", sondern **„warten, bis genug JS geladen/geparst/ausgeführt ist, damit React den `useEffect` für `mounted` (Zeile 214-215, `setTimeout(…, 0)`) und den Zustand-Rehydrierungs-Callback überhaupt laufen lassen kann"** — bei 21,7 s gemessener Main-Thread-Arbeit (M2) dauert das in dieser Umgebung mehrere Sekunden.
4. **Schlussfolgerung:** Der `opacity:0`-Gate in `HomeClientV2.tsx` (M1-Hypothese) war real vorhanden, aber **nicht die wirksame Ursache** — die Seite kam nie so weit, dass dieser Gate überhaupt zum Tragen kam, weil `MainLayout` das komplette Kind-Rendering schon vorher blockierte. M1s Diagnose hat den richtigen Ort (LCP-Element, 92 % Render-Delay) korrekt gemessen, aber den Mechanismus falsch zugeordnet — ein Fall von Korrelation (Code direkt um das LCP-Element herum) statt Kausalität (Code weiter oben im Baum).

### Zusatz-Erkenntnis (Tooling-Caveat, nicht App-Bug)

Live-Prüfung im Browser-Pane über `element.getAnimations()` zeigte `currentTime: 0`, `startTime: 0` dauerhaft trotz `playState: "running"` — das CSS-Animations-Timing lief nie weiter. Ursache: Der `computer`-Screenshot-Aufruf schlug mit „the Browser pane is not displayed, so the page is not compositing frames" fehl — **das Browser-Pane dieser Session komponiert in diesem Kontext keine Frames**, wodurch rAF-/CSS-Animation-Uhren pausiert bleiben. Das ist ein Artefakt dieses Werkzeugs/dieser Session, **keine reale Auswirkung für einen normalen Browser-Tab bei Jan** — die Lighthouse-CLI-Messung (eigene, echte Headless-Chrome-Instanz) ist davon unberührt und bleibt die maßgebliche Zahl.

- **Bewusst nicht in dieser Ausführung angefasst:** `MainLayout.tsx`-Änderung würde **jede** Route der App betreffen (nicht nur die Homepage), das Mount/Hydration-Gate existiert vermutlich zur Vermeidung von SSR-Hydration-Mismatches (verbreitetes Next.js-Muster) — Entfernen/Abschwächen ohne eigene Risikoprüfung wäre grober Scope-Bruch (M2-Scope war exklusiv `HomeClientV2.tsx`/`globals.css`) und ein deutlich höheres Risiko (App-weiter Blast-Radius) als alles bisher in dieser Initiative Umgesetzte — braucht einen eigenen Plan mit eigener Selbstprüfung, nicht einen angehängten Schnellschuss.

Fix ist sauber, sinnvoll (Design-Erhalt + Accessibility + geringfügige Main-Thread-Verbesserung) und bleibt im Code — löst aber nicht das eigentliche LCP-Problem.

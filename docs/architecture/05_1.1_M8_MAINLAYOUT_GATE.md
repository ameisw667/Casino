**Kernbefund aus der Datenfluss-Analyse (M8.1, bereits abgeschlossen):**

- `useCasinoStore` nutzt `skipHydration: true` — der Store startet auf dem Client **mit denselben Default-Werten wie beim Server-Render**, bis `MainLayout` manuell `.rehydrate()` aufruft (Zeile 201). Das heißt: **Server-HTML und Client-Erstrender sind bereits identisch, bevor Hydration überhaupt beginnt** — genau die Bedingung, unter der ein Mount-Gate keinen Hydration-Mismatch verhindert, sondern nur unnötig wartet.
- `balance`, `xp`, `level`, `rank`, `bets`, `allBets`, `isMobile` sind **explizit von der Persistierung ausgeschlossen** (`partialize`, Zeile 930-949) — sie ändern sich nie durch `.rehydrate()`, sondern ausschließlich über einen separaten, von `hasHydrated` unabhängigen Effekt (`applyServerWalletSnapshot`, Zeile 252-274). Das Gate schützt diese Felder also **gar nicht**.
- Die einzigen in `MainLayout` gelesenen, tatsächlich persistierten Felder sind `hideBalance` (Default `false`) und `communityWagered`/`communityGoal` (Defaults `8420.5`/`25000.0`) — beide primitive, crash-sichere Werte. Bei Entfernen des `hasHydrated`-Gates zeigt die Seite für den Bruchteil einer Sekunde die Default-Werte, bevor `.rehydrate()` sie durch die echten gespeicherten Werte ersetzt — ein kosmetisches Aufblitzen einer Einstellung, **kein struktureller Layout-Unterschied, kein Absturz, kein React-Hydration-Mismatch-Fehler**.
- `_hasHydrated` wird **ausschließlich** in `MainLayout.tsx` gelesen (verifiziert: `grep -rl "_hasHydrated\|hasHydrated" src` → nur Store-Definition, Store-Test, `MainLayout.tsx`). Keine andere Komponente hängt daran.

**Nächster Schritt:** M8.2–M8.6 direkt ausführen (risikoarm laut Analyse, keine gesonderte Rückfrage nötig über das bereits erteilte Go hinaus).

### M8.2 — Shared Hook extrahieren

**Neu:** `src/hooks/useMounted.ts`

```tsx
import { useSyncExternalStore } from 'react';

const emptySubscribe = () => () => {};

/** Client-mount detection without an effect + setState (avoids the extra
 * render pass and hydration flash that useState+useEffect(() => setMounted(true)) causes). */
export function useMounted(): boolean {
  return useSyncExternalStore(
    emptySubscribe,
    () => true,
    () => false,
  );
}
```

**Ergebnis erneut unmissverständlich: keine Wirkung auf das LCP-Ziel.** Der `curl`-Rohdaten-Check zeigt weiterhin „INITIALIZING CASINO..." im SSR-HTML — das ist **erwartet und korrekt**, kein Fehlschlag: `useSyncExternalStore`s `getServerSnapshot` liefert serverseitig immer `false`, ein Server kann per Definition nicht „mounted" sein. ### Einordnung: warum der (korrekte, sauber verifizierte) Fix trotzdem nichts bringt

Der M8-Fix beseitigt zwei reale, aber **kleine** Ineffizienzen: einen unnötigen zusätzlichen Render-Pass (`setTimeout(0)`) und ein unnötiges Warten auf den Persist-Rehydrate-Rückruf, obwohl keine der in `MainLayout` gelesenen Store-Felder das bräuchte (Abschnitt 1, Kernbefund). Beide Ineffizienzen liegen in der Größenordnung von **Millisekunden**. Der gemessene Engpass liegt bei **~5.200 ms Render-Delay** und **~28 s Main-Thread-Arbeit** (throttled) — verursacht durch das schiere Volumen an JS (374 KB, 20 Chunks), das geladen, geparst und ausgeführt werden muss, bevor React überhaupt das erste Mal committen kann. **Kein Gate-Mechanismus — egal wie effizient — kann schneller sein als die Zeit, die der Browser braucht, um genug JS lauffähig zu haben.** Das ist jetzt zum dritten Mal bestätigt (M2: Opacity-Mechanismus, M8: Mount-Mechanismus) — beide Hypothesen zielten auf den _Gate_, nicht auf das _JS-Volumen dahinter_. Die Ursache liegt strukturell woanders: bei dem, was tatsächlich main-thread-Zeit kostet (WebGL-Init, Scroll-Hooks, Bundle-Größe) — genau das, was M3/M4/M5 als Nächstes angehen.

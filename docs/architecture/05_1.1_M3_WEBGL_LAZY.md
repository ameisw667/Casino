## 1 — Befund vor Umsetzung (wichtig, ändert den ursprünglichen Auftrag)

H5 aus M1 lautete „WebGL-Guards laufen trotzdem mit messbarem Anteil, laufzeit-ungeprüft". Code-Lesung beider Komponenten zeigt: **die Guards sind bereits korrekt und vollständig implementiert**, nicht mangelhaft:

- `WebGlWaterRefractionCanvas.tsx:63-69`: bricht **vor** jeglicher WebGL-Initialisierung ab, wenn `matchMedia('(max-width: 1023px)').matches` oder `isMobile` — inkl. explizitem Kommentar, warum der synchrone `matchMedia`-Check zusätzlich zum (asynchron nachziehenden) Store-`isMobile` nötig ist. Rendert `null` (Zeile 195-200) auf Mobile — **kein Canvas-DOM-Element, kein WebGL-Context, kein rAF-Loop**.
- `LobbyAmbientBackground.tsx:28`: identisches `matchMedia`-Gate ganz am Anfang des Effekts — auf Mobile läuft **kein** Partikel-Loop, kein Resize-/Mousemove-Listener.

**Was die Guards NICHT verhindern:** Beide Komponenten werden aktuell **statisch importiert** (`HeroCinematicShowcase.tsx:16`, `HomeClientV2.tsx:12`) — der komplette Code (inkl. GLSL-Shader-Strings, Partikel-Logik) wird auf **jedem** Gerät heruntergeladen, geparst und kompiliert, bevor der Guard überhaupt zur Laufzeit greift. Der reale Hebel ist also nicht „Guard reparieren" (schon korrekt), sondern **„Bytes, die auf Mobile ohnehin nie ausgeführt werden, gar nicht erst mitschicken"** — Bundle-Ebene statt Runtime-Ebene.

## 2 — Implementierung

- `HeroCinematicShowcase.tsx`: `import { WebGlWaterRefractionCanvas } from '@/components/home/WebGlWaterRefractionCanvas';` → `import dynamic from 'next/dynamic'; const WebGlWaterRefractionCanvas = dynamic(() => import('@/components/home/WebGlWaterRefractionCanvas').then((m) => m.WebGlWaterRefractionCanvas), { ssr: false });`
- `HomeClientV2.tsx`: identische Umstellung für `LobbyAmbientBackground` (Named statt Default Export — `.then((m) => m.LobbyAmbientBackground)`).
- Keine Props-/Verhaltensänderung — beide Komponenten bekommen weiterhin `isMobile`/keine Props wie zuvor.

## 4 — Verifizierung & Ergebnis (ausgeführt 2026-08-09)

### Umsetzung (erweitert gegenüber Abschnitt 2 — Grund siehe unten)

- `HeroCinematicShowcase.tsx`/`HomeClientV2.tsx`: `WebGlWaterRefractionCanvas`/`LobbyAmbientBackground` auf `next/dynamic({ssr:false})` umgestellt (wie geplant).
- **Erste Messung (nur `dynamic()`, ohne Mount-Gate): 0 Bytes gespart** — 374 KB Transfer unverändert, da `next/dynamic` den Chunk trotzdem fetcht, sobald die Komponente irgendwo gerendert wird, unabhängig vom internen `matchMedia`-Guard.
- **Erweiterung:** Neuer Hook `src/hooks/useIsNarrowViewport.ts` (`useSyncExternalStore`, gleicher 1023px-Breakpoint) gated jetzt zusätzlich den **Mount-Punkt** von `WebGlWaterRefractionCanvas` in `HeroCinematicShowcase.tsx` (`{!isNarrowViewport && <WebGlWaterRefractionCanvas .../>}`) — sicher, da die Komponente auf Mobile ohnehin `null` rendert (0 visueller Unterschied, siehe Abschnitt 1 Befund).
- **`LobbyAmbientBackground` bewusst NICHT zusätzlich gegated** — anders als beim WebGL-Canvas rendert diese Komponente auf Mobile noch sichtbaren Inhalt (statisches Spotlight-Glow + Noise-Textur, nur die Partikel-Animation ist gegated) — ein Mount-Gate hätte das entfernt, das ist eine echte visuelle Änderung und braucht Jans Freigabe, nicht Teil dieses risikoarmen Schritts.
- **Selbst gefundener und korrigierter Fehler:** Erster Hook-Entwurf setzte `getServerSnapshot() => false` (analog zum Store-Default) — das fetcht den Chunk trotzdem, weil `next/dynamic` den `import()` beim ersten (falschen) Render auslöst, bevor die Client-Korrektur greift. Per Netzwerk-Log nachgewiesen (Shader-Chunk war im ersten Durchlauf fälschlich in der Fetch-Liste). Korrigiert: `getServerSnapshot() => true` (im Zweifel „schmal" annehmen) — danach strukturell bestätigt (Shader-Chunk-Grep gegen tatsächliche Netzwerk-Requests): **Chunk wird auf Mobile nicht mehr angefragt.**

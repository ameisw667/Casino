**Warum das kein Fehlschlag der Vorgehensweise ist:** Jede der 5 Maßnahmen war einzeln begründet, korrekt umgesetzt, korrekt verifiziert (`tsc`/`lint`/`build` grün, kein Regressions-Risiko) und ehrlich nachgemessen — genau das Vorgehen, das falsche Annahmen aufdeckt statt sie zu verstecken. Das eigentliche Ergebnis dieser Initiative ist **die Erkenntnis selbst**: LCP in dieser Messumgebung wird von der **Grundlast** dominiert — React/ReactDOM- + Zustand-Store- + Supabase-Client-Initialisierung (die 3 größten, architektonisch notwendigen Chunks, siehe M1) plus dem CPU-Throttling-Profil dieser Sandbox-Umgebung —, nicht von einem einzelnen behebbaren Bug. Keine der 5 Maßnahmen konnte das ändern, weil keine an der Grundlast selbst ansetzte (das hätte eine der beiden großen Optionen gebraucht: (a) weniger JS vor dem ersten sinnvollen Paint laden — z. B. echtes Server-Rendering der Hero-Sektion statt vollständigem Client-Rendering hinter `MainLayout`s Shell, oder (b) prüfen, ob das Throttling-Profil dieser Sandbox-Messumgebung härter ist als reale Zielgeräte).

**Ehrliche Grenze dieser Initiative:** Ob (b) zutrifft, lässt sich von hier aus nicht klären — die Original-Baseline (2026-07-28, Performance 56) und alle 5 Nachmessungen dieser Session liefen auf unterschiedlicher, nicht direkt vergleichbarer Hardware (siehe M1-Methodik-Hinweis). Eine Messung auf einem echten Mobilgerät oder in einer nicht-virtualisierten Umgebung wäre der einzige Weg, (a) von (b) zu trennen — das ist außerhalb dessen, was in dieser Sandbox-Session möglich ist.

**Empfehlung für eine mögliche Folge-Initiative (nicht Teil dieses Plans, nicht gestartet):** Falls Jan das LCP-Ziel weiterverfolgen will, wäre der nächste sinnvolle Schritt **nicht** eine sechste clientseitige Mikro-Optimierung, sondern entweder (a) eine echte Messung auf einem realen Mobilgerät, um den Sandbox-Throttling-Verdacht zu prüfen, oder (b) eine größere Architektur-Untersuchung, ob die Hero-Sektion serverseitig vorgerendert werden kann, statt komplett hinter `MainLayout`s Client-Gate zu hängen.

### Hauptbefund: LCP-Element identifiziert + Root Cause

- **LCP-Element:** `<span>` mit Text „VIP CASINO." innerhalb `<h1>` in `HeroCinematicShowcase` (CSS-Pfad `section > div > h1 > span`).
- **LCP-Zeitaufteilung (Lighthouse-Audit):** TTFB 8 % (461 ms) · Load Delay 0 % · Load Time 0 % · **Render Delay 92 % (5.145 ms von 5.605 ms Gesamt-LCP)**.
- **Root Cause:** `src/components/home/HomeClientV2.tsx` rendert den gesamten Homepage-Baum in `<motion.main initial={{ opacity: 0 }} animate={{ opacity: 1 }}>` — **die komplette Seite inklusive der LCP-Headline ist unsichtbar (opacity: 0), bis Framer-Motion nach vollständiger JS-Hydration die Transition ausführt.**
- **Live-Verifikation im Browser (anonyme Session, `localhost:3021`):** `getComputedStyle(document.querySelector('main.vibe-mesh')).opacity` lieferte **`"0"`** unmittelbar nach Laden **und erneut nach +2 s Wartezeit** — die Seite blieb über den gesamten Beobachtungszeitraum unsichtbar. Damit ist der Render-Delay-Anteil (92 %) strukturell erklärt, unabhängig vom Umgebungs-Throttling-Vorbehalt oben: Der Text existiert im SSR-HTML (daher niedrige TTFB), wird aber erst sichtbar, wenn JS geladen, geparst, hydratisiert **und** die Opacity-Transition ausgeführt hat.
